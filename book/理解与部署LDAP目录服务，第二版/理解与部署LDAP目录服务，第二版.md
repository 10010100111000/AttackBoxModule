你拿起这本书并开始阅读，说明你对目录服务及其作用有所了解。本章假设你对目录服务有日常的了解，并在此基础上展开，解答三个简单但重要的问题。

什么是目录？ 简而言之，目录是一种专门的数据库。本章将介绍目录的特殊之处、它与传统数据库的区别、目录的定义特征以及这些特征的重要性。

目录能为你做什么？ 目录的功能非常广泛，你选择这本书很可能是因为你心中已经有了想要利用目录来解决的特定问题。我们将带你了解目录的基本用途（其中许多你可能已经想到过），同时也会介绍一些你可能还不熟悉的更高级的用法。

什么不是目录？ 在构建一个成功的目录环境时，这个问题的答案有时比学习目录的概念更为重要。本章将阐述目录与文件系统、Web 服务器以及网络中部署的其他服务之间的区别。这些区别对于缩小目录服务的设计范围至关重要。

本章旨在详细解答上述每个问题，并将答案系统化，以便您在设计目录服务之前对任务有一个共同的理解。您将了解目录的重要性、目录解决方案的范围以及目录能为您带来哪些好处。在本章末尾，我们将通过探讨轻量级目录访问协议 ( LDAP) 的历史和起源来介绍它。掌握这些知识后，您就可以继续阅读本书的其余部分，这些部分将详细介绍如何理解、设计、部署、维护和使用您自己的目录服务。

**目录服务定义**

本书会引入不少陌生术语。**目录服务**由软件、硬件、流程、策略与管理规程共同构成，用于向使用本目录的用户提供目录信息。目录服务至少包含以下组件：

- 目录中保存的信息 
- 存放这些信息的软件服务器 
- 代表用户或其他实体访问该信息的软件客户端 
- 这些客户端和服务器运行所依赖的硬件
- 支持软件，例如操作系统和设备驱动程序
- 连接客户端和服务器以及服务器之间的网络基础设施
- 关于谁可以访问和更新目录、目录中可以存储什么内容等等的策略
- 目录服务的维护和监控流程
- 用于维护和监控目录服务的软件

如您所见，这确实是一个相当长的列表！[ 图 1.1]展示了其中一些组件。通常，我们会将 *“目录”* 一词作为 *“目录服务”* 的同义词。请务必记住，您的目录是一个由多个组件组成的复杂系统，这些组件协同工作以提供服务。如果只关注其中一组组件而忽略其他组件，肯定会导致问题。

### 什么是目录

大多数人或多或少都接触过各类目录，只是未必意识到这一点。目录存在于我们日常生活之中。我们日常见到的目录实例包括电话簿（白页、黄页）、电视节目指南、商品目录、图书馆卡片目录等等。我们把这类目录称为**日常目录**，有时也叫**离线目录**。

以这些例子为例，很明显，目录通过描述和整理待查找的物品来帮助人们找到所需信息。这类目录中的信息涵盖范围很广，从电话号码到电视节目，从消费品到参考资料等等。

计算机和网络领域的目录在很多方面都很相似，但也存在一些重要的差异。我们称这些目录*为在线目录* 。在线目录与离线目录的区别如下：

- 在线目录是*动态的* 。
- 在线目录具有*灵活性* 。
- 在线目录可以做到*安全可靠* 。
- 在线目录可以*个性化定制* 。
- 以下各节将探讨这些差异。

了解不同类型的目录也很重要。我们将目录分为以下几类：

- **应用专用目录（Application-specific directories）** 这类目录随应用附带，或是内嵌在应用内部。很多时候你甚至不会把它们看作目录，因为其功能和所属应用深度耦合。例子包括 IBM/Lotus Notes 的姓名地址簿、微软 Exchange 目录，以及 sendmail 消息传输代理（MTA）所使用的 aliases（别名）文件。
- **基于网络操作系统（NOS）的目录（Network operating system (NOS)–based directories）** 这类目录是为满足网络操作系统的需求而设计，例如 Novell 的 eDirectory（最初名为 NetWare 目录服务，简称 NDS）、微软 Active Directory、Sun 微系统公司的网络信息服务（NIS），以及 Banyan 的 StreetTalk 目录。
- **专用目的目录（Purpose-specific directories）** 这类目录不绑定某个应用，但是服务于单一、限定的用途，**不具备可扩展性**。典型例子：互联网域名系统（DNS），以及 Switchboard 这类互联网集中式电话目录（http://www.switchboard.com/）。
- **基于标准的通用目录（General-purpose, standards-based directories）** 这类目录的设计目标是支撑种类繁多的各类应用。本书重点介绍的 LDAP 目录、基于 X.500 的目录都属于这一类。

本章会提及以上四类目录。不过，本书的核心重点正是**通用型目录**。

##### 目录具有动态性

你所熟悉的日常目录相对静态，也就是不会频繁变更。例如电话簿一年才更新一版；想要获取最新信息，你就得拨打 411 这类公共查号服务。电视节目指南每周都会出新刊，但你喜欢的节目仍可能毫无预告地被临时撤档，这种情况比你预想的更多。邮寄送到你手上的商品目录，一年最多更新数次；而且这类目录不会包含库存状态、商品颜色与尺码等实用信息。为什么？因为这类信息变化太快，等目录送到你手中时，内容就已经过时了。

与之相反，**在线目录**可以持续保持数据最新。当然，这个特性并非总能发挥作用：目录的数据新鲜度，取决于管理员的维护策略。有时会部署管理流程，实现目录的自动更新。如果目录本身作为所存储信息的**权威数据源**，在线目录往往能发挥最佳效果。信息一旦发生变更，就可以在目录内完成更新，并立刻提供给用户使用。

不难理解，在线更新能力可以提升目录数据准确度，让目录更实用。这类改进属于**渐进式优化**。但在线更新能力同样能带来颠覆性的革新。这些革新催生了全新的目录应用场景，这类场景是离线目录完全无法实现的。

举个例子：假设目录保存了组织内员工的在岗信息。门禁读卡器可查询这份目录，以此授权人员进出公司楼宇与房间。在该场景下，管理员只需修改目录中的信息，就能**即时、便捷地撤销人员访问权限**。

再举一例：目录存储人员位置信息，当你在不同办公室、酒店房间或其他地点之间移动时，位置信息会持续更新。系统可查询这份目录，把你的电话、传真、消息路由到你当前所在位置。传统纸质目录永远无法实现这类功能。这类应用的本质，就要求信息能够高频更新。

在线目录强大的更新能力，不仅能够让信息保持最新，还可以**下放更新责任**。信息离数据源越近，数据就越可能准确、及时，原因至少有三点：

1. 顾名思义，数据源本身掌握的信息是最准确的。
2. 如果由数据源直接执行更新，就能消除数据源到目录之间额外的延迟与出错可能性。
3. 根据信息类型与应用场景，数据源往往最有动力维护信息的正确性。

我们沿用前面的位置目录例子来说明。数据源就是用户本人（也就是你），信息是你的当前位置。还有谁能比你更清楚自己在哪里？哪种更新路径更可靠：由你直接提交，还是通过行政助理代为录入（暂且不论你的打字水平）？设想一下：信息先由你告知助理，再由助理转告目录管理员，最后由管理员录入目录。每多一道中转环节，就多一分出错概率，准确性随之下降，同时参与人员增多，成本也会上升。最后，谁最关心目录里你的信息是否准确？答案同样是作为数据源的你。因为一旦信息有误，你就无法收到转接的电话、传真和邮件。当然，这个例子有前提假设：你有足够责任心保证信息准确，并且拥有完成更新所需的工具与操作能力。

### 目录具备灵活性

静态的日常目录与在线目录之间还有一项重要差异：在线目录在两个方面拥有高得多的灵活性：

- 可存储的信息类型
- 信息的组织方式与检索方式

#### 灵活的内容

离线目录在内容层面是固化的。也就是说，离线目录所能承载的信息集合是受限的，且很少扩展。举例来说，如果你想查询电话簿提供的姓名、地址、电话号码之外的信息，基本无法实现。但还有大量其他有价值的信息同样有保存需求，例如传真号、手机号、寻呼机号码、电子邮箱，甚至照片、简短个人简介，这些都和传统电话簿信息属于同一类身份数据，但纸质目录几乎不会收录。

与之相反，在线目录可以轻松新增各类信息类型。对于纸质目录而言，增加这类信息的成本极高；而在线目录的新增成本相对很低。纸质目录一旦要新增内容，就必须重新设计、重印、再分发，代价巨大；而且旧版目录的印刷成本几乎无法复用。

但在线目录在设计上通常支持**直接扩展，无需重新整体设计**。它不需要重印，所有修改会自动、即时生效；也不需要重新分发目录副本，因为客户端采用在线访问，不会在本地保存完整副本。部分客户端可能会缓存或复制部分数据，但这些副本可以自动更新。

出于成本与实际落地的考量，纸质目录一般不会采用这种扩展方式，除非绝大多数目录用户强烈要求新增这类信息。第一，作为纸质目录的制作方，若无充分理由，你无法承受为增加信息而把目录篇幅扩大一倍甚至两倍，这会让制作成本同步翻番。第二，从实际使用角度看，目录体量会变得臃肿笨重，反而给目标用户带来不便。

而在线目录则不存在这类高昂成本，可直接扩展。哪怕新增的数据项只有少数用户使用，也具备成本效益。新增字段带来的开销是**增量式**的，是在基础服务成本之上额外增加的少量投入。可能仅需要为系统扩容磁盘，备份耗时、管理与运维成本小幅上升。而且普通用户完全不会感受到任何不便 —— 他们甚至看不到新增的信息。有需求的用户则可以轻松获取新增数据。同时这还存在商业激励：你可以针对这类增值目录服务单独收费。

#### 灵活的数据组织方式

在线目录灵活性的第二个体现，在于其数据组织形式。我们继续沿用电话簿的例子。电话簿存储姓名、电话号码、地址信息，**数据组织方式是为按姓名检索而优化**。如果你想按电话号码或者地址来检索，至少可以说，操作会十分困难。

市面上可能存在其他专门为这类检索场景设计的专用目录，但无法保证不同组织形式的目录之间数据一致。按姓名编排的电话簿，其数据时效性，和按号码编排的专用电话簿可能有差异。这类目录会存在**数据冗余**，往往引发数据不一致、信息过时等问题。此外，这类专用目录通常不易获取，而且成本高昂。纸质目录能支持的数据组织形式本身就有限，同时还受限于载体（例如纸张）以及终端使用者的能力（使用者可能没有受过专业训练）。

与之相反，在线目录**可以同时支持多种数据组织形式**。相当于纸质电话簿的在线目录，能轻松支持按姓名、号码、地址或其他字段检索。除此之外，在线目录还能够实现更高级的检索，这类检索在纸质载体上很难实现，甚至完全无法实现。

举个例子：如果你不确定某个姓名的拼写，在线目录可以帮你检索**读音近似**的名字。它还支持基于常见拼写错误、名字子串以及其他变体形式进行检索。这些不同类型的检索可以并行执行，或是按预设顺序依次执行（例如先精确匹配，再读音近似匹配，接着子串匹配，以此类推），直到找到匹配条目为止。这种强大的检索能力，是实现用户所期望的**“懂我意图”**查询效果的关键。

### 目录可具备安全能力

离线目录几乎没有安全保护能力。例如电话簿本身就是公开资料。企业内部印制的纸质通讯录，或许会用红色大字标注 “禁止对外分发”，但这种安全管控最多只能算作**劝告性约束**。这类安全短板限制了离线目录能支撑的应用场景，同时迫使用户做出两难选择（如果还有选择余地的话）。大多数人都了解**未列入名录的电话号码**，这是多数电话公司提供的增值付费服务。选择不把号码录入目录，能减少推销电话等骚扰来电，但同时，你希望联系到的人也无法查到这个号码。

问题根源在于离线目录本身不存在安全机制。目录里的数据，要么**所有拿到目录的人都能查看**；要么直接不录入目录，任何人都无法获取。该局限是离线目录分发与访问方式带来的必然结果：纸质目录分发范围广，每个人都能拿到副本；访问方式就是翻书，或是拨打 411 这类公共查号服务。这些方式都无法识别访问者身份，自然也就无法控制该用户可以查看哪些信息。

在线目录能够解决上述问题。在线目录将信息集中存储，从而可以对信息访问行为实施管控。访问目录的客户端可以通过**身份认证（authentication）**机制完成身份识别。简单来说，身份认证就是目录客户端向目录服务证明自身身份的过程，客户端一般会提交凭证（例如密码），以此证明自己就是所声称的主体。

结合**访问控制列表（ACL）**以及其他信息（如访问时段、客户端 IP 地址），目录可以利用认证阶段确认的身份，执行**授权判定**：决定哪些客户端能够访问目录中的哪些数据。

继续沿用电话簿的类比，我们看看 ACL 这类安全特性会带来什么样的改变。你的信息可以录入目录，但**仅允许一部分目录客户端查看**。你可以把这部分人指定为你的好友列表，也可以按条件设定，例如 “所有住在我所在街区的人”。你也可以设置为：除指定黑名单人员外，所有人均可查看你的信息。这类配置方案十分丰富，能力强大。

但需要认识到：即便拥有如此强大、灵活的安全能力，它也**并非万能灵药**。举个例子：一名受信任的员工，直接把屏幕上的机密信息复制下来并对外分发，这种情况下 ACL 防护会被绕过，尽管这种攻击方式不算便捷。即便存在这类局限，在线目录的安全能力依旧远优于离线目录。

### 目录支持个性化

纸质目录与在线目录的另一项差异，是二者所能实现的个性化程度。个性化包含两个维度：

- 向目录用户**个性化交付服务**
- 对目录内存储的信息**做个性化访问管控**

《电视节目指南》与电话簿仅能按地域做有限的个性化。图书馆里所有人使用同一套卡片目录，大家收到的 L.L.Bean 商品目录也完全相同。同一地区内的所有人拿到的电话簿、电视指南内容都一模一样。如果能收到贴合个人兴趣的商品目录、按你偏好的检索方式编排的电话簿，或是能记住你读书偏好的图书卡片目录，将会十分理想。这就是个性化的第一个维度：**面向信息使用者，提供按需定制的信息**。

个性化的第二个维度，关乎你能否自主决定谁可以查看你的信息及其他相关数据。也就是**作为信息提供方，按自身需求对目录进行自定义配置**。正如前文所述，在离线目录中，针对你个人信息的可见性，你只有两个粗粒度选项：录入目录，或是完全不录入，没有中间选项。而且很多目录甚至连这个选择都不提供。想要把自己的信息从名录中移除，过程往往繁琐耗时，令人沮丧。

在线目录同时具备上述两项能力。实现该能力的底层机制，正是前面介绍的目录安全能力。在线目录可以识别访问者，并存储用户的配置档案信息，从而为不同用户提供目录的**个性化视图**。举个例子：在线商品目录可以向你展示最可能感兴趣的商品。这类个性化服务，既可以基于你主动声明的兴趣偏好，也可以基于你过往与该服务的交互记录。

从用户角度来看，这类个性化体验十分友好，因为它提供了更贴合需求的服务。用户无需在大量无关信息里费力翻找，才能定位自己想要的内容。从服务提供商的角度，个性化同样具备很高价值：既能向用户提供更优质的服务，也便于服务商精准推送各类特色服务。例如，服务商可以根据用户偏好，定向推送促销活动、新品信息以及广告。当然，部分用户会对个人信息的采集范围与使用方式提出隐私顾虑。因此，成熟的服务商总会在目录服务中配套提供灵活的隐私管控功能。

### 目录的定义阐述

到目前为止，我们对**目录（directory）**的讨论，主要依靠常识层面的理解。我们借助大家熟悉的纸质日常目录，解释在线目录是什么，以及它和离线目录的差异。现在，我们从前面的讨论中提炼在线目录的核心特征。下文给出的定义并非严谨的形式化定义，也不是数学定义；取而代之，我们将详细阐述在线目录共有的一系列特征。

------

#### 设计中心（Design Center）的定义

**设计中心（design center）**这一术语，指驱动系统设计与落地实现的一整套核心假设、约束条件与评判标准。在设计或实现一套系统时，你需要做出一系列取舍判断：哪些是重点、哪些不重要，哪些功能系统必须做到优秀，哪些可以适当降低标准。一套系统的**设计中心**，体现了设计者 / 实施者在做这些决策时的核心关注点。设计中心这一概念同样适用于软件、其他各类系统与产品。

举个例子，假设你要为自己设计并制造一台交通工具。除了满足几项基础特征（本质上就是带轮子的机动运载工具）之外，你拥有很大的设计自由度。 如果设计者家里人口多，可能会设计旅行轿车或厢式面包车，其**设计中心**就聚焦于大载客量。 另一位需要经常运送大量货物的设计者，可能会设计卡车，她的设计中心重点就是载货能力。 而一名驾驶爱好者做设计，则会把性能与操控性作为核心。

软件与服务的设计中心遵循相同逻辑。设计者通常会思考一系列问题，以此确定合适的设计中心，例如：这套软件系统或服务面向大规模群体还是小规模群体？目标用户是技术专业人员还是缺乏经验的普通使用者？性能是否是系统的关键指标？安全性是否属于核心指标？ 这些问题以及其他问题的答案，决定了设计与实施工作的重心，最终塑造整个系统的特性。

目录可以看作一类专用数据库。对比数据库与目录十分有意义：二者的差异更多来自**运行环境与设计中心**，而非底层基础原理。做这项对比还有一个好处：大多数人对数据库的概念与功能，比对目录更加熟悉。通用数据库与通用目录之间的差异，主要分为下面几大类：

- **读写比（Read-to-write ratio）**：目录的读写比通常高于数据库。
- **可扩展性（Extensibility）**：目录一般比数据库更容易扩展。
- **分发规模（Distribution scale）**：目录数据的分发范围通常比数据库更广。
- **复制规模（Replication scale）**：目录的数据复制规模往往大于数据库。
- **性能（Performance）**：目录与数据库具备不同的性能特征。
- **标准（Standards）**：对目录而言，遵循标准的重要性高于数据库。
- **事务与连接查询（Transactions and join）**：目录通常不支持事务，也不支持`JOIN`这类关系型运算。

本节后续内容会对以上每一点逐一解释。

目录的一项核心特征：**查询 / 读取操作的频次，远高于写入 / 更新操作**。数据库却未必如此。 有些数据库用来存储审计数据，这类数据只在特殊场景（或是极少场景）才会被读取。举例来说，这类数据每天会产生数千次写入（每一笔数据库事务生成一条记录），但每月仅读取一次用于生成汇总报表，或是每年内部审计时才读取一次。

而目录中的信息，读取次数通常远多于写入次数。实际上，目录单条信息的读取频次达到写入频次的上千甚至上万倍，是很常见的情况。只要想一想目录通常存放的数据类型，就不难理解。以人员信息为例，这类数据变更频率相对很低，但查询访问的次数非常多。对比一下：你更换手机号的频率，和别人拨打你电话的次数；你变更住址的频率，和你收到邮件的次数。

具备这种 “读多写少” 特征的数据，并不局限于人员信息。商品目录数据、大部分位置信息、配置信息、网络路由信息、参考资料等，全都是读取远多于写入。目录能够支撑的应用场景范围很广。部分场景下，数据不会在线实时更新，而是由管理员定期执行批处理任务来完成更新。

为什么这项特性十分重要？它确立了目录实现的**设计中心**。开发人员可以基于该特性做出关键的简化设计决策。目录实现可以针对高频执行的操作做深度优化。倘若目录设计者已知读取与检索操作的调用频次是更新操作的一万倍，就可以投入更多精力来提升读操作的执行速度。与之对比，数据库在设计时，通常要求写入与读取操作都具备良好性能。目录针对读密集型应用做优化这一特性，也会对目录的其他功能（例如后续将要讨论的复制）产生影响。

### 信息可扩展性

目录另一项重要的核心特征，是支持**信息可扩展性**。**目录模式（directory schema）**这一术语，**指可存储的信息类型、信息必须遵守的规则，以及信息的行为特征**。LDAP 目录的模式设计会在本书第 8 章《模式设计》中详细探讨。

目录并不局限于一套固定不变的模式来完成数据存储与查询。模式可以根据新需求、新应用进行扩展。**目录一般自带一套实用的预定义信息类型**，但很多部署环境存在特殊需求，需要对这套预定义集合进行扩展。你的组织可能需要保存一些自定义字段（在目录术语中称为**属性（attributes）**），例如员工的在岗状态，或是打印机所在楼宇的位置编码。绝大多数目录都允许向已有的目录对象新增这类属性，并且不会破坏已经存在的数据。

虽然数据库可以存储多种多样、组织形式各异的数据，但它对可存储的数据类型往往存在约束，部分数据库很难为已有记录新增字段。几乎没有数据库支持引入具备全新语义的原始基础数据类型；但部分目录却支持新增这类原始数据类型。

虽然有些数据库允许有限的数据分布，但分布规模却各不相同。典型的关系型数据库管理系统允许您将一个表存储在某个位置，另一个表存储在另一个位置。这种分布通常仅限于少数几个站点。虽然可以执行涉及两个站点的查询，但性能往往是个问题，导致数据分布功能很少被使用。

数据分布是目录设计中的一项基础要素。目录的设计目标之一，就是支持数据在网络的不同区域之间分布。该能力用于满足**权限与管理职能必须分布式落地**的场景。 举例：某组织在全球多个国家设有分支机构，就需要这类分布式能力。每个分支机构希望能够管理自己辖区内的目录数据；而组织整体又需要对外呈现**单一的逻辑目录**。

数据分布的重要性还体现在支持大规模目录方面。随着目录数据量的增长，购买更大服务器（配备更多磁盘空间、内存和 CPU 性能）的策略最终会带来收益递减。

更好的方法是使用一组小型机器来构建目录，这些机器协同工作以提供整体服务。在许多情况下，这种方案成本更低。它的优势在于可以利用所有承载目录的机器的并行处理能力，从而提高读写性能。此外，即使一台机器发生故障，也不会导致整个服务瘫痪。而且，它对某些系统管理功能（例如执行备份、灾难恢复等）的性能也具有显著的实际意义。例如，假设一个目录分布在十台小型机器上：备份或恢复其中一台小型机器比备份或恢复一台大型机器要容易得多。

数据分布式存储允许将信息存储在需要使用信息的应用程序和人员附近。例如，假设有三个应用程序需要使用目录信息：员工查询工具（在线电话簿）、将电话系统配置信息存储在目录中的专用交换机 ( PBX ) 以及将用户配置文件信息存储在目录中的网络操作系统（例如 Microsoft Windows NT）。通过数据分布式存储，可以将这三个应用程序各自的特定数据存储在靠近应用程序的目录服务器上，从而提高效率并避免每个应用程序的私有数据重复存储。

#### 数据复制

与数据分发密切相关的是数据复制。 *数据复制*是指在不同位置维护目录数据的多个副本。这样做有几个原因：

可靠性。如果由于硬件或软件故障导致某个目录副本无法访问，仍然可以访问其他副本。

可用性。即使部分网络发生故障，客户端也更有可能找到可用的副本。

本地性。如果客户端距离目录副本更近，则可以降低延迟和性能波动。

性能方面* ，** 随着副本数量的增加，可以处理更多查询，从而提高目录服务的整体吞吐量。

数据库有时支持复制，但通常只支持少量副本，而目录通常支持数十个副本。长期以来，数据库复制实现的性能一直是个大问题，部分原因是数据库复制几乎总是强一致性的；也就是说，所有数据副本必须始终保持同步。通常，必须采用分布式跨网络锁定机制，并使用两阶段提交算法才能实现数据库更新的强一致性。

另一方面，**目录复制几乎总是松散一致性的**。这意味着不同副本中包含的数据存在暂时性不一致是可以接受的。这一特性对目录可支持的副本数量以及这些副本在网络中的物理分布有着重要影响。

正如您将在本节后面了解到的，性能是目录的一个重要特性。确保目录性能良好的一个好方法是确保目录的每个用户都拥有该目录的副本。这样做有两个原因：

1. 将目录数据移至靠近访问它的客户端的位置，可以减少目录请求的网络延迟，这通常会提高整体吞吐量，并提高每次目录操作的性能一致性。
2. 通过增加副本，可以提高整个系统处理的目录查询总数。如果一台目录服务器每天可以处理 100 万次查询，那么增加一台服务器就可以将系统容量提升到每天 200 万次查询。这种通过增加副本来处理更多负载的技术通常被称为*水平扩展* 。

目录的可用性也是一个关键因素。许多不同的应用程序通常会使用目录来实现诸如身份验证、访问控制和配置管理等基本功能。如果这些应用程序想要正常运行，目录必须始终可用。

请注意，可用性与可靠性并非同一概念。一个可靠的目录服务器可能配备冗余硬件和不间断电源。这样的目录服务器几乎不会宕机，但这并不意味着它始终可供需要访问的客户端使用。例如，连接客户端和服务器的网络段可能会出现故障。从客户端的角度来看，这与目录服务器硬件或软件宕机造成的问题相同。

您可以尝试通过在网络中构建与服务器相同的硬件可靠性来解决这个问题。冗余、不间断电源和其他技术都很有价值，尽管并非总是切实可行。另一种方法是复制目录数据，使数据更靠近需要访问的客户端。这种方法有助于缓解可能导致客户端无法访问目录的网络问题。[ 图 1.4] 显示了一个未复制的示例场景，[ 图 1.5]显示了一个已复制的示例场景。

#### 性能

如前所述，高性能是目录服务与数据库的另一大区别。数据库性能通常以每秒可处理的事务数来衡量。这同样也是衡量目录服务性能的重要指标，但目录服务的要求与大多数数据库系统的要求有所不同。

一个典型的大型数据库系统每秒可能处理数百个事务。而一个典型的大型目录系统所需的总目录性能可能达到每秒数千甚至数万次查询。这些查询通常比数据库处理的复杂事务要简单得多。如前所述，目录的读写比通常远高于数据库。因此，对于目录而言，更新性能不像对数据库那样至关重要。不过，正如您将在本节后面了解到的，更新性能仍然非常重要。

目录查询性能要求的提高部分原因在于，使用该目录的应用程序种类繁多。数据库的设计和部署可能只考虑单个或少数几个驱动应用程序，而目录通常作为基础设施组件部署，供公司内部乃至整个互联网上数量未知但不断增长的应用程序使用。目录的访问权限是分布式的，导致这些访问的应用程序的开发也是如此。这意味着，作为目录管理员，您通常无法控制目录必须响应的查询类型。因此，目录必须具备灵活性，并且无论需要响应何种类型的查询，都能保持良好的性能。

目录性能要求还取决于通常访问目录的应用程序类型。应用程序访问目录的目的多种多样。例如，如果您的电子邮件软件使用目录来路由电子邮件，则每封邮件都需要进行一次或多次目录查找。根据您的网站处理的邮件量，这可能会给目录带来相当大的负载。

许多应用程序都需要高性能。如果您的目录被 Web 应用程序用作身份验证数据库，那么每次用户启动新应用程序时都会访问该目录。如果这些应用程序使用您的目录来存储用户偏好设置和其他用于实现位置无关性的信息，则需要进行更多目录访问。如果您的目录用于存储 Web 服务器、邮件服务器和其他服务器的配置和访问控制信息，那么每次客户端访问这些服务时都可能需要访问该目录。用户数量庞大时，这将迅速累积成巨大的网络流量。在这些环境中，利用目录本地性来最大限度地减少网络延迟对于提供足够的性能至关重要。

如您所见，目录是许多对性能要求极高的操作的核心。当然，客户端缓存可以而且应该用于减少目录本身的访问次数，但即使是这些技术也只能减缓目录查询的速度。高性能仍然是目录最重要的特性之一。

我们之前提到过，目录的读写比很高。由此很容易得出这样的结论：写入性能远不如读取和搜索性能重要。虽然这在某种程度上是正确的，但某些目录处理的数据规模使得写入性能也成为一个重要因素。而且，正如我们之前所述，在线更新能力是某些令人兴奋的新型在线目录应用程序的关键驱动力之一。显然，更新能力至关重要，而且必须达到一定的性能水平。

例如，假设一个目录包含 100 万条记录。这看起来很多，但对于电商网站或大型企业来说并非不合理（前提是已为所有用户、用户组、网络设备、外部合作伙伴、客户和其他信息添加了记录）。如果每条记录平均每月只更改一次，那么每月就有 100 万次更新，每周 25 万次更新，每天近 3.6 万次更新，或每小时约 1500 次更新。这更新量相当惊人！而且，由于用户发起的更改通常发生在工作时间内，因此每小时需要处理的更新峰值会更高。管理员发起的更改可能需要保存并在有限的非高峰时段批量应用，这会进一步影响性能。

#### 标准与互操作性

通用目录与通用数据库的另一个重要区别在于标准。数据库领域存在各种伪标准，从关系模型本身到结构化查询语言 ( SQL )。这些伪标准使得从一个数据库系统迁移到另一个数据库系统更加容易。它们还使得用户在掌握了某个供应商系统背后的概念后，可以轻松地将这些知识应用到其他供应商的系统中，从而快速上手。然而，这些标准并不能提供真正的互操作性。在目录领域，由于任何供应商的应用程序都必须能够使用该目录，因此真正的互操作性标准至关重要。

这就是轻量级目录访问协议 (LDAP) 的用武之地 。LDAP 提供了当今现代目录所使用的标准模型和协议 。LDAP 使得微软开发的客户端能够与 Netscape 开发的服务器协同工作，反之亦然 。LDAP 还使您能够开发可与任何目录配合使用的应用程序。在数据库领域，Oracle 应用程序无法与 Informix 数据库一起使用，Informix 应用程序也无法与 Sybase 数据库一起使用。这种数据库所缺乏的互操作性对于目录至关重要，原因有二：

1. 它允许将目录客户端与目录服务器解耦。
2. 它允许将应用程序开发过程与特定目录供应商的决策解耦。

在 LDAP 出现之前，每个需要目录的应用程序通常都会内置自己的目录。乍一看，这似乎是一个便捷的解决方案，但当你安装了第二十四个应用程序（也就是第二十四个目录）之后，问题的弊端就显而易见了。组织中每个需要访问这些应用程序的用户都需要在每个目录中创建一个条目——这意味着需要维护大量重复信息。[ 如图 1.6]所示，所有这些重复数据都是系统管理员头疼的主要来源，也是信息技术 ( IT ) 部门成本增加的主要原因。

### 事务与连接查询

目录仅支持相对简单的事务模型。目录事务**只包含单个操作、仅作用于单条目录条目**。与之相反，数据库在设计上通常可以处理复杂多样的事务，这类事务能够跨多条记录，包含一连串操作。数据库提供**回滚（rollback）**能力：当一组事务操作未能全部完成时，可以撤销这组操作，将数据恢复至原始状态。当事务执行到后半段发生错误时，回滚机制就非常有用。对部分应用场景而言，数据库提供的完整事务支持至关重要。注意：部分目录软件会通过 LDAP 基础标准之上的私有扩展，来实现数据库风格的事务。

除此之外，当前主流数据库大多是关系型数据库，支持**连接查询（join）**。连接查询是一类查询，利用公共键值，把来自多个数据源（数据表）的关联数据合并为一个结果集。绝大多数目录完全不支持连接查询。

举一个适合使用连接查询的场景：假设你需要查询**产品开发部员工所管理的全部打印机对象**。进一步假设：每个人对象都有员工编号字段，每个打印机对象有所有者字段，该字段同样存储员工编号；同时人对象中存在部门字段。此时，借助连接查询，通过人员条目把打印机对象和产品开发部进行匹配，就能轻松得到目标结果集。在 SQL 中，这类查询大致写法如下：

```
Select *
  From PrinterTable A, EmployeeTable B
  Where A.OwnerID = B.EmployeeID AND Department = 
    "Product Development";
```

如果用目录来获取同样的结果集，则需要执行多次查询。一种实现思路：先查询出产品开发部的所有人员（一次查询）；再针对查到的每一名人员，检索所有者 ID 匹配该员工编号的打印机（多次查询）。由此可见，关系型数据库管理系统（RDBMS）的连接查询能力十分强大。但并非所有应用场景都需要该能力。

### 总结

简单概括：**目录是一类专用数据库，其读取与检索操作远多于写入操作**。目录通常支持存储多种类型信息，并提供机制扩展可存储的数据类型。目录既可以集中部署，也可以分布式部署；无论从数据分发方式还是部署位置来看，目录常采用大规模分布式架构。目录一般会开启复制，保障客户端访问的高可用。目录复制规模可达到数百甚至数千个副本。复制同时还能提升目录性能，这一点至关重要，它为应用提供了一套可放心使用、快速可靠的基础设施组件。最后，LDAP 协议让目录实现了标准化。标准化使得不同厂商的应用与服务端可以独立开发、销售与部署。目录并不支持数据库所具备的复杂事务与连接查询。

### 目录可以为你带来什么

我们已经讨论过日常生活中会接触到的各类离线目录服务应用。也介绍过：依托在线目录的实时更新能力、可扩展特性与个性化能力，这些传统应用可以得到优化，有时甚至会迎来颠覆性变革。现在，我们把关注点完全转向在线目录这一引人关注的方面：充分利用在线目录的全部能力，可以开发出哪些全新的应用。

#### 信息查找

正如本章开篇所说，绝大多数日常目录都是为了解决**信息查找**的问题。例如在图书馆找到想要的图书；查询朋友或商户的电话号码；从商品目录里找到想要订购衬衫的款式、尺码与颜色；或是查询今晚想看的电视节目的播出时间与频道。传统目录对信息做整理编排，方便人们找到目标内容。信息查找同样也是在线目录的重要应用。并且正如接下来会看到的，在线目录的能力，可以实现更加高级的查找方式。

在线目录最基础、最广为人知的应用，就是**线上版电话簿**。 这类目录分为两端：一端是互联网目录服务商提供的覆盖整个互联网、全国范围的大型目录，例如 Switchboard。 而另一端，你可以利用目录技术，为本组织搭建一套本地电话簿。

这些在线目录所提供的服务和纸质目录大体相似，但存在几处关键区别。

第一，在线目录可以极大提升目录的规模与覆盖范围。举个例子，Bigfoot 目录几乎整合了北美的全部电话簿。试想，如果要在家里存放这么多本纸质电话簿以供随时查阅，几乎不现实。 更重要的是，即便是电话簿这样简单的场景，在线目录也能够用新颖的方式组织信息。例如，你不仅可以按姓名、电话号码、地址检索，还可以检索传统电话簿根本不会收录的其他信息。 当你不知道姓名的正确拼写、怀疑号码错了一位数字，或者只记得姓名的部分字符时，你还可以执行各类新型检索。除此之外，你还可以采用多种不同方式浏览目录内容。

#### 检索与浏览

目录通常同时支持**检索（searching）**与**浏览（browsing）**，但你必须分清二者的区别。

继续用离线目录类比，就能很清楚地看到，检索和浏览两种能力都是必需的。 如果你想查皮特披萨外卖店的电话号码，目标明确，希望直接拿到结果。电话簿按字母排序，方便你快速定位，这就是**检索**。

而当你想买新衣服时，很少能精准确定要买哪一件。你心里可能只有大致特征（知道自己的喜好、当下想要的风格），不太可能清楚衬衫的品牌与款式。这时你会翻阅商品目录，浏览服装图片，直到找到心仪的商品，这就是**浏览**。

浏览与检索**并非互斥**。很多场景下，你先通过检索缩小候选范围，再对结果进行浏览；也有反向场景：先浏览可选条目，找到范围后再执行检索。需要记住的重点是：浏览和检索是**互补关系**。部分应用只需要其中一种，部分应用两者都需要，可组合使用，也可在不同时段分别使用。

这种灵活的搜索和浏览方式直接源于目录能够同时以不同方式组织信息。这种灵活性在各种应用中都至关重要。例如，考虑一个网络打印应用程序。该应用程序允许用户选择所需的打印机属性。这些属性可能包括位置、彩色或黑白、打印质量、纸张尺寸或类型、单面或双面打印功能等等。典型的用户交互可能包括用户选择最重要的属性（例如，颜色和打印质量）。然后，用户可以从打印机列表中进行选择，例如根据位置选择打印机。

最后举个例子来说明如何查找服务。假设一位客户正在网络上寻找某项服务。这项服务可以是数据库服务、员工福利登记服务、股票报告或交易服务、在线约会服务、特定学科的研究服务，或者几乎任何其他类型的服务。只要这些服务在目录中注册，用户或其他应用程序就可以随时查询目录来找到它们。目录的在线更新功能使得用户即使服务变更了位置，也能找到所需的服务。服务商只需更新目录中的新位置即可。

#### 资源管理

在线目录与离线目录的一个显著区别在于信息管理。在线目录在分布式环境中扮演着管理核心角色，为需要管理的对象提供了一个集中式存储库。该领域最常被提及的案例，就是开销巨大的用户与用户组管理，这也是目录能够提供的最重要的管理服务之一。集中式目录可以大幅降低这项服务的运维成本。

设想这样的场景：一名用户需要访问网络上全部已部署应用，就必须在每一个应用专属的目录中新建该用户账号。一旦用户的某项信息发生变更，就必须在所有这些目录中逐一修改。这就是著名的 N+1 目录问题：每新增一套应用，就多出一套需要维护的目录。这给各地管理员带来麻烦，同时增加运维成本。终端用户同样会深受其扰。举个例子，如果环境内一共有 24 套目录，每套目录都保存一份该用户的密码。在缺少同步机制的前提下，修改其中一处密码，其余 23 处密码不会同步更新。

试想部署一套集中式目录之后，局面会发生怎样的改变。此时你**只需要在一处录入或修改用户信息**。网络中新增应用时，直接复用这套集中目录，不再使用自身的私有目录。密码的存储与修改也统一在这一处完成。当然，这个理想方案存在显而易见的短板：所有应用都必须改造，至少要支持选用集中式目录，放弃各自专有的私有目录。

将用户和组信息存储在集中式目录中，也能让应用程序开发人员受益。他们无需为每个应用程序开发集成专有目录服务的方案，而是可以利用现有资源，专注于开发更优质的应用程序。

目录在解决管理问题方面还能发挥重要作用，例如配置管理。传统上，应用程序的配置信息保存在一组文件或操作系统特定的存储库中，例如 Microsoft Windows 注册表。这种解决方案易于实现，并且对许多应用程序来说都适用。但网络应用程序通常有不同的需求，尤其是在大规模部署时。

例如，考虑一个 Web 服务器网络。一家大型企业可能拥有数百台服务器。如果它们共享一个或多个配置项，想象一下修改所有服务器配置的繁琐工作。如果采用配置文件的方式，您需要访问每台 Web 服务器并编辑其配置文件。对于数百台服务器来说，这项任务确实非常繁琐。您可以基于 rdist 和 rsync 等工具开发一个临时的配置管理系统，但系统本身也需要管理。

现在考虑一下这些服务器将配置信息存储在集中式目录中的影响。首先，可以实现对服务器的远程管理；可以从网络上的任何位置访问服务器的配置。其次，配置可以在服务器之间共享，从而实现服务器集群管理。在我们之前的示例中，数百台 Web 服务器的配置可以从中心位置快速轻松地更改。[ 图 1.8]展示了这种场景的示例。

![图 1.8. 使用目录进行集中式配置管理](./image/Chapter%201%20Directory%20Services%20Overview%20and%20History/01fig08.webp)

目录管理的一个类似且可能更强大的应用领域是用户配置和偏好设置。与应用程序配置类似，用户偏好设置历来都保存在配置文件或本地数据库中，例如 Microsoft Windows 注册表、Unix 系统主目录中的点文件以及 Macintosh 的偏好设置文件。在集中式用户配置管理至关重要的环境中（这样的环境有很多），这种方式显然不太方便。然而，如果应用程序能够从目录中存储和读取这些信息，就可以一次性更改数千个用户配置。试想一下，只需在前一天晚上在一个地方更改一个配置设置，第二天用户上班启动应用程序时，配置就能无缝生效。

当这种方法与在目录中存储用户特定状态信息相结合时，即可实现位置无关性。这在许多环境中都是一项重要的特性。例如，假设一位用户需要在家里的电脑和公司电脑上访问应用程序。该用户可能已经根据自己的喜好设置了偏好。或许她需要在每个地点访问个人电子邮件地址簿，或者在浏览器中保存个人书签。将这些信息存储在目录中并从网络中检索，即可确保用户在家和公司都能拥有相同的环境。

在车间、医院或大学校园等场所，也存在类似的需求，这些场所为没有固定电脑的用户提供自助服务终端。我们用 *“漫游”* 一词来描述这类用户；这种不为员工提供固定办公空间的新兴做法有时被称为 *“共享办公”* 。 信息系统专业人员和其他需要在日常工作中接触到多种不同电脑的人员，也可以从目录实现的地点独立性中受益。[ 图 1.9]展示了这种应用。

#### 轻量级数据库应用程序

本章第一节通过与数据库的比较，对目录进行了描述。本节将更详细地探讨两者之间的区别。目录擅长存储和检索相对较小的信息片段。**LDAP 目录提供标准协议和标准 API 来访问这些信息**，这一点也很有吸引力。在 LDAP 出现之前，需要维护简单数据库的应用程序开发人员只有几种选择：

- 构建一个专有的专用数据库。这种方法意味着应用程序开发人员和应用程序管理员需要付出额外的工作量，因为他们必须安装和维护数据库。这也意味着浪费大量时间去解决那些原本已经解决的问题。
- 嵌入商业数据库软件包。这种方法更具吸引力，因为它通常能减少应用程序开发人员的工作量，并避免重复劳动。然而，对于必须安装和维护数据库的用户和管理员来说，仍然会有些不便。嵌入像 Oracle 这样功能齐全的数据库是过度设计，而且价格昂贵。虽然也存在其他更简单的嵌入式数据库，但它们通常是专有的，难以集成。

嵌入一个简单的目录服务器通常可以解决同样的问题，并且还有一些明显的优势。目录通常比功能齐全的数据库更小、更简单。LDAP 目录提供了一种标准的访问协议，这意味着您的应用程序可以与其他目录交互，其他应用程序也可以访问您的目录。这种方法有助于避免前面提到的 N+1 目录问题。

LDAP 目录还提供事实上的（即将成为正式的）标准 API，您可以使用这些 API 访问目录，从而提高应用程序的可移植性。最终，应用程序员将目录服务嵌入应用程序所需的工作量将大大减少。

Netscape 的网页浏览器和邮件客户端就是一个嵌入式数据库的例子。该客户端维护着多个本地数据库，其中包含用户书签、本地地址簿信息、安全信息和其他信息。过去，所有这些数据都存储在各自独立的专有数据库中，这意味着信息无法共享，也只能在本地计算机上访问。引入目录服务器来存储这些信息，就能解决这两个问题。

Netscape 证书管理系统是嵌入式数据库的另一个例子。该服务器维护着一个数据库，其中包含其颁发给用户的证书。产品 1.0 版本将这些证书存储在 Informix 数据库中。事实证明，这种方法笨重、难以管理和安装，总体而言并非理想之选。现在，证书服务器使用嵌入式 LDAP 目录服务器来管理此信息数据库。这种基于目录的解决方案更易于安装和管理，更易于开发，也更加灵活。

#### 安全应用程序

目录的另一个有趣应用领域是安全。尤其值得关注的是基于公钥的安全系统。第 12 章 “隐私和安全设计”将更详细地介绍这些系统。目前，我们只需知道，提供此类安全所需的公钥基础设施 ( PKI ) 管理起来非常困难。PKI 需要一种方法将证书等安全对象分发给客户端和服务器，保持这些安全对象的更新，在它们被泄露时撤销它们，并处理其他功能。如果没有目录，这些任务将难以完成。

目录有助于解决证书和公钥基础设施 (PKI) 通常引入的两个问题：

1. PKI 生命周期管理问题。这个问题与证书的创建、维护和销毁方式有关。如果没有目录，这个过程就需要您自行管理。如果您运气好，或许有一些专有软件可以代表您执行这些操作，帮助您管理整个流程。
2. 证书位置问题。这个问题涉及如何找到你想与之安全通信的人的证书，以及想与你通信的人如何找到你的证书。如果没有证书目录，你和你的朋友可能不得不互相打电话，然后念出一串串十六进制（以 16 为基数）数字。

引入目录有助于解决这两个问题。该目录在整个 PKI 生命周期中充当中央管理点。您的各种安全对象甚至可以存储在目录中，由您或您信任的管理员进行维护。当您需要新证书时，可以通过该目录轻松获得证书。当需要撤销证书时，该目录同样提供了快速高效的撤销方式，以及通知其他相关方变更的途径。

该目录还有助于查找其他用户的证书。在本应用中，证书或其他安全信息只是用户目录条目的另一个属性。从目录中检索证书与检索姓名、电话号码或电子邮件地址一样便捷高效。[ 第 12 章]将对这些问题和流程进行更详细、更正式的描述。

### 目录不是什么

根据我们的经验，人们在了解目录时有时会产生两种极端反应。一种反应是负面的：“这个目录到底有什么用？为什么我不能直接用 X 来满足同样的需求？我不认为这个目录能像你说的那么可靠、性能那么好，我不敢让我的应用程序依赖于它！”这种反应通常可以通过进一步的讲解来消除，帮助持怀疑态度的人了解目录的实际应用，并更好地解释目录的种种优势。

还有另一种同样存在误区、但更难纠正的想法：“这个目录太棒了！我觉得它无所不能。我可以用目录替代文件系统、Web 服务器、FTP 服务器以及一大堆其他组件。终于有这么一个好用的全能工具，既能切又能剁，还能做手工甜点，最厉害的是还能自动清洁！”

这种热情值得肯定，但其中同样暗藏风险。有句老话是这样说的：**如果你手里只有一把锤子，那么所有问题看起来都像钉子。**不必多说，并非所有问题都是钉子；强行把所有问题都当成钉子来处理，最终只会得到糟糕的木工活。

目录也是如此；和其他任何技术一样，它最适合解决特定类型的问题。目录也可以应用于许多其他问题，尽管效果可能略逊一筹。试图让目录解决它原本不打算解决的问题，就可能滥用目录的功能。

本节我们将更深入地探讨这一领域，并解释目录*不*适合的诸多应用场景。我们将阐述目录为何与以下表面上看似相似的网络服务有所不同：

- Databases
- File systems
- Web servers
- FTP servers
- DNS servers

我们将解释您的目录如何与所有这些服务相辅相成，以及为什么每项服务都能在您的计算基础架构中发挥重要作用。本节最后，我们将总结何时使用目录存储信息，何时使用其他方式。

#### 目录 VS 数据库

本章第一节介绍了目录的概念，并将目录与数据库进行了比较。这里不再赘述比较内容，但会重点强调几个要点。首先，需要注意的是，目录通常是读取为主的，而非写入为主的。因此，如果您的应用程序需要写入大量数据（例如，用于记录商品交易），则应选择数据库而非目录。

其次，目录服务器支持相对简单的事务模型。目录事务仅涉及单个操作和单个目录条目。而数据库则旨在处理大型且多样化的事务，这些事务跨越多个数据项和众多操作。数据库还支持连接操作，从而可以高效地生成复杂的结果集。如果您的应用程序需要这种支持，那么数据库比目录服务器更合适。另一方面，如果您的应用程序没有这些要求，而只是想以简单的事务方式从网络访问的数据库读取信息（偶尔写入），那么目录服务器可能是一个不错的选择，它经济高效，而且比 Oracle 关系数据库之类的方案要简单得多。

#### 目录 VS 文件系统

目录并非理想的文件系统。文件与目录信息具有不同的特性。文件通常很大，包含数兆字节甚至数千兆字节的信息，而目录则针对存储和检索相对较小的信息块进行了优化。

虽然目录项或属性的大小通常没有限制，但这取决于设计中心。有些文件的写入频率远高于读取频率，例如日志文件和用于存储数据库的文件。您应该记得，目录的设计目标是优先考虑读取而非写入。当然，有些文件的读取频率远高于写入频率。应用程序二进制文件就是这类文件的典型例子，但这些文件的大小通常远大于目录存储所需的大小。

应用程序通常会分块访问文件，尤其是在文件较大时。文件系统 API 提供了诸如 seek() 、 read() 和 write() 等函数来专门实现这一目的，这些函数可用于仅访问较大文件的一部分。目录不支持这种随机访问。相反，目录条目被分割成称为*属性*的数据项，例如电话号码和姓名。您可以单独检索每个属性，但通常必须检索请求的任何属性的全部内容。与文件系统不同，目录无法从特定字节偏移量开始仅检索属性的一部分。另一方面，文件系统不擅长存储基于属性的信息，并且通常不具备目录所拥有的通用搜索功能。

#### 目录 VS  Web 服务

自 20 世纪 90 年代中期万维网横空出世以来，Web 服务器已变得无处不在。您的组织很可能运行着一台到数百台 Web 服务器，具体数量取决于其规模。Web 服务器与文件系统在某些方面有相似之处。它们旨在为访问大小差异巨大的文档或文件的客户端提供服务。虽然 Web 服务器文档通常具有目录信息典型的“多读少写”特性，但目录并不适合向客户端提供数兆字节的 JPEG 图像或 Java 应用程序。

Web 服务器通常也作为 Web 应用程序开发平台的跳板。这些平台种类繁多，从简单的 CGI （通用网关接口）到更复杂的平台，例如 BEA 的 WebLogic 应用服务器或 Sun 的 ONE 应用服务器。目录服务器通常不具备这种应用程序开发的灵活性，尽管某些目录服务器实现（例如 Netscape Directory Server）确实提供了一个平台和一组可用于目录应用程序开发的服务。

目录服务器经过优化，能够对其存储的数据进行高级搜索。Web 服务器也可用于开发类似的搜索应用程序，但此类应用程序并非基于标准。Web 服务器侧重于为应用程序提供图形用户界面 (GUI) 界面，而非为应用程序提供对目录数据的通用访问。如果您有一个特定的信息数据库需要向用户开放，那么 Web 服务器可能是一个不错的选择。但如果您需要将信息提供给各种应用程序，那么目录服务器则是更佳的选择。

#### 目录 VS  FTP 服务

与之前针对 Web 服务器的论点类似，文件传输协议（ FTP ）服务器也同样适用。有人可能会认为，随着 Web 服务器的普及， FTP 服务器的时代即将终结，但目录服务的出现并不会对其构成威胁。同样，主要的区别在于数据的大小以及需要访问数据的客户端类型。另一个重点是， FTP 协议本身很简单，它专注于做好一件事。如果你只想创建一个将文件从一个地方传输到另一个地方的方法，那么执行复制、搜索、更新等操作所需的额外目录基础设施就显得多余了。

另一方面，如果您的应用涉及的信息检索和存储不仅仅是简单的操作，那么目录是更合适的选择。与目录不同， FTP 不提供搜索功能、基于属性的信息模型以及增量更新功能。

#### 目录 VS DNS 服务

DNS，即互联网域名系统，负责将主机名（例如 home.netscape.com ）转换为 IP 地址。主机名便于用户记住如何连接到他们常用的互联网服务。IP 地址则是互联网网络基础设施所必需的，它负责建立用户连接。DNS 和普通目录有一些相似之处，例如都提供对分层分布式数据库的访问。但两者之间也存在一些重要的区别。

DNS 针对其主要用途进行了高度优化；大多数目录则更通用。DNS 拥有一套专门的、固定的模式集； 目录允许扩展模式。DNS 服务器通常不允许更新其信息； 目录则允许。DNS 可以通过无连接传输访问；目录通常通过基于连接的传输访问。

#### 互补型目录

目录和上面提到的诸多服务存在一定相似性，但目录更多是对这些服务形成**互补**。接下来我们探讨**互补型目录**这一概念，理解它的含义，以及它如何在企业内所有服务之间产生协同效应。

目录与 Web 服务器的协作，就是互补型目录的绝佳示例。在此场景中，目录承担几项重要的支撑角色。

第一，目录可作为**认证数据库**。客户端向 Web 服务器发起身份认证时，Web 服务器会到目录校验用户凭证（例如用户 ID 与密码，或是数字证书）。当 Web 服务器需要执行访问控制判断时，同样可以查询目录，获取用户所属组以及其他和权限判定相关的信息。 当环境内部署多台 Web 服务器，并且全部需要使用同一套认证库时，目录的价值就尤为突出。多台 Web 服务器共用一套目录，把用户管理的复杂度降到可控范围。其他服务同样可以采用这种方式获益。

第二，目录可作为**可通过网络访问的存储载体**，存放配置信息、访问控制策略、用户偏好与用户档案等各类数据。目录在该场景下的价值体现在两方面：

如果这类信息需要在多台服务器间共享，目录可以充当集中存储库，消除重复运维工作，原理和它管理用户与用户组信息一样。正如本章前文所述：若要在 100 台 Web 服务器上修改同一条共享配置，只需要在目录中执行一次更新，会方便很多。 如果不使用目录，就只能逐台登录 Web 服务器重复修改，或是单独搭建一套临时专用系统来管理配置。

目录还提供一套**标准化、可网络访问**的方式来管理上述全部信息。这为标准化管理工具、统一运维框架创造了大量新的可能性。

作为目录互补特性的第三个示例：目录可以协助整理并访问 Web 服务器内部存储的信息。如今已有各类 Web 搜索引擎，用于收录、整理网页内容。但只要经常使用搜索引擎的人都会体会到：你往往要花费大量时间筛选大量无关结果，真正阅读目标信息的时间反而更少。问题根源在于 Web 内容本身缺少结构化，很难通过自动化手段完成整理与检索。XML（可扩展标记语言）问世之后，这种缺少结构化的局面才开始改善，而目录就可以在此场景发挥作用。

目录非常擅长整理信息，并支持后续对信息的访问。试想由目录驱动的下一代 Web 搜索引擎：使用目录查询语言，通过描述信息结构，能够更加精准地定义你想要查找的内容，目录就可以返回相关性高度聚焦的结果集。需要注意，在这套方案中，**原始内容仍然保存在 Web 服务器中**，全文自由文本检索依旧沿用现有方式。目录的价值，是在这套架构之上增加一层结构化能力，同时提供一套既精准又灵活的查询机制。

文件系统与 FTP 服务器，是体现目录互补能力的又一个典型案例。此时目录并不存储文件本身的内容，而是保存文件的**元数据**：文件存放位置、文件所有者，以及其他有助于定位文件的信息。最重要的是，目录可以保存文件系统、FTP 客户端访问文件时所需的各类信息。FTP 服务器同样可以将目录服务器用作身份认证服务。

借助目录来整理、检索待访问资源，是一个很核心的设计思路。目录通常并不保存你想要获取的原始内容；它存储的是内容的位置信息，外加其他辅助查找的属性。

哪些数据适合放在目录，哪些应当存放在别处，二者的分界线并不总是清晰明确。通用参考原则如下：

- 信息体量越大，就越不适合存入目录；
- 信息更新越频繁，就越不适合交由目录维护；
- 信息结构化程度越低，存入目录带来的收益就越少；
- 反之，信息被共享的场景越多，存入目录带来的收益就越高。

下面是一份简明参考，用于判断应当选用目录还是其他技术存储数据：

1. **信息体量**：目录最适合存储体量较小的数据，不适合存放数兆字节的大文件。目录适合保存指向大型资源的**指针**，而不是直接存储大型资源本身。
2. **信息特征**：目录采用**基于属性**的信息模型，信息被拆解为一组**键‑值对（name‑value pairs）**（详细讲解 LDAP 信息模型，请参考：《LDAP 简介》一章）。如果你的业务信息可以很自然地表达为键‑值形式，目录会是不错的选择；如果做不到，则优先考虑数据库、文件系统或其他方案。
3. **读写比**：目录最适合读远多于写的数据。如果数据写入操作十分频繁，数据库或文件系统会更加合适。
4. **检索能力**：目录就是为检索内部数据而设计。如果应用有强检索需求，目录是合适选项。
5. **基于标准的访问**：如果你需要依靠开放标准访问数据，目录是很好的选择。

在为应用选择存储方案时牢记这些原则，能帮你避开很多陷阱。读到这里，你应当已经清楚目录是什么、目录不是什么，以及目录与网络中其他服务之间的关系。希望这些知识可以帮你避开**“锤子综合征”**：不要把所有问题都看作钉子，试图用目录这把锤子去解决一切。



### LDAP 的历史和起源

本章第一部分介绍了在线目录的概念，并将其与各种其他基于网络的服务和协议进行了比较。现在我们已经深入讨论了目录的功能，接下来将讨论 LDAP 以及通用、基于标准的在线目录的起源。

#### 标准目录的曙光：X.500

如果不先提及 X.500，就无法讨论 LDAP 的起源。20 世纪 80 年代中期，两个独立的标准组织分别着手开发能够跨越系统、企业和国际边界的目录服务。第一个组织是国际电报电话咨询委员会 ( CCITT )，后来更名为国际电信联盟 ( ITU )。CCITT 的成员组织（主要是电话公司）希望创建一个白页目录，用于查找电话号码和电子邮件地址。

另一个标准组织是**国际标准化组织（ISO）**，它希望构建一套目录，作为**开放系统互连（OSI）**网络与应用的**名称服务**。（名称服务用于提供网络对象的相关信息；DNS 就是大家熟悉的例子。）

最终，两个独立的目录规范项目合并为一个项目，X.500 由此诞生。第一个 X.500 标准于 1988 年底获得批准，并于 1990 年初由 CCITT 发布；随后分别于 1993 年、1997 年和 2001 年进行了更新（至今仍在进行）。该规范本身引用了其他 ISO 标准，并包含一系列建议，其中包括：

- X.501：模型。描述了 X.500 目录服务的基本概念和模型。
- X.509：身份验证框架。详细描述了 X.500 中如何处理目录客户端和服务器的身份验证。
- X.511：抽象服务定义。详细描述了 X.500 目录提供的功能服务（例如，搜索操作、修改操作等）。
- X.518：分布式操作程序。除其他细节外，还描述了如何处理跨多个服务器的目录操作。
- X.519：协议规范。描述了所有 X.500 协议，包括目录访问协议 ( DAP )、目录系统协议 ( DSP )、目录操作绑定协议 ( DOP ) 和目录信息影子协议 ( DISP )。
- X.520：选定的属性类型。定义了 X.500 本身使用的属性类型，以及一些通常也很有用的属性类型（例如 `telephoneNumber` 属性）。
- X.521：选定的对象类 。定义了 X.500 本身使用的对象类，以及一些通常也很有用的对象类（例如 `person` 对象类）。
- X.525：复制。描述如何在 X.500 服务器之间复制目录内容。
- X.530：系统管理。描述了如何通过使用 OSI 系统管理服务和协议、目录服务和协议以及本地方式来管理 X.500 目录服务。

正如您所见，X.500 开发人员在开始开发 X.500 目录服务软件之前，必须阅读相当多的文档！这些 X.500 文档由国际电信联盟 (ITU) 以在线和纸质两种形式发布，目前获取这些文档需要付费。

##### X.500 创新

X.500 在最初定义时就具备许多创新特性。首先，它是最早真正意义上的通用目录系统之一，从一开始就被设计成可扩展的，以满足各种应用程序的需求。其次，X.500 提供了丰富的搜索功能，支持多种类型的查询。第三，X.500 被设计成一个高度分布式的系统，服务器、数据和管理员可以遍布全球。最后，X.500 是一个开放标准，不受任何单一厂商的控制，也不依赖于任何特定的操作系统、网络技术或应用程序。X.500 设计者的愿景是最终建立一个完全互联的全球目录服务：目录系统（ *Directory* ）。[ 图 1.10]展示了 X.500 目录服务的主要组成部分。

X.500 目录依赖于一系列协议，包括 DAP 、 DSP 、 DOP 和 DISP。X.500 的一些优势在于其灵活且完整的信息模型、通用性和开放性。正如您将看到的， LDAP 设计者借鉴了 X.500 的许多优秀理念，同时消除了不必要的复杂性。

##### X.500 缺陷

实际上，X.500 目录存在一些重大缺陷，尤其是在其诞生的最初十年。早期的实现存在诸多漏洞，性能和扩展性都很差。尝试部署分布式 X.500 目录的用户发现，推广应用面临着诸多障碍，其中许多障碍并非 X.500 特有（例如，难以获取和维护目录服务中的高质量数据）。此外，由于标准本身的复杂性以及相关的实施难度，不同 X.500 实现之间的互操作性也经历了漫长的实现过程。

此外，X.500 基于 OSI 网络协议。OSI 设计者的梦想是 OSI 最终能够取代 TCP/ IP， 成为未来的网络协议套件。可惜的是，这个梦想最终未能实现。TCP/ IP 的简洁性、速度和低成本优势使其脱颖而出，成为无可匹敌的竞争者。事实上，最近 X.500 的支持者们已经定义了一种映射，使得 X.500 可以直接运行在 TCP/ IP 之上。

最后，X.500 本身的起源在某种程度上阻碍了它的成功。互联网的快速发展是自下而上实现的，各个独立组织按照自己的节奏部署主机和服务，很少依赖其他组织。相比之下，X.500 的设计初衷是服务于大型公共服务提供商，这意味着它采用的是自上而下的部署方式。事实证明，自上而下的部署方式是无法实现的——而且它显然与当前的互联网文化格格不入。

#### X.500 早期实施和试点

早期最著名的 X.500 实现之一名为 Quipu，由伦敦大学学院开发。它的名字来源于印加文化用于通信的复杂绳结系统。Quipu 早期流行的原因之一是它以源代码形式免费提供。Quipu 构建于名为 ISO 开发环境 ( ISODE ) 的 OSI 网络软件包之上，该软件包允许 OSI 协议运行在 TCP/ IP 之上，从而实现互联网连接。

Quipu 的推出促使许多机构尝试使用 X.500 目录。Quipu 的实现为欧洲和美国的多个 X.500 白页应用试点项目奠定了基础。遗憾的是，这些全球性的 X.500 目录试点项目的发展速度并未达到发起者的预期，人们的兴趣也逐渐减弱。

X.500 在大型组织中取得了最大的成功，这些组织有能力投入时间和精力来部署大型、复杂的目录服务。X.500 的早期部署者包括英国学术界、波音公司、美国国家航空航天局 ( NASA )、德克萨斯大学和密歇根大学。尽管如今所有 X.500 产品都可以通过 LDAP 以及 X.500 协议访问，但它们仍然可用。通常，X.500 目录服务的部署是与 X.500 软件供应商合作完成的。大多数供应商都提供全面的咨询服务，帮助组织将 X.500 目录部署并集成到其现有环境中。

#### LDAP 的创建与兴起

X.500 的早期用户发现， DAP （X.500 的目录客户端访问协议）相当复杂，而且并不适合当时的台式电脑 （PC 和 Macintosh），也无法在台式电脑上运行。DAP 体积庞大、结构复杂、难以实现，而且大多数实现的性能都很差。由于大多数潜在的目录用户都使用普通的台式电脑，因此 X.500 的部署人员开始寻找一种能够避免使用重量级 DAP 的方法。

##### LDAP 的前身： DIXIE 和 DAS

大约在 1990 年，两个独立的研究小组设计了类似的协议，与 DAP 相比，这些协议更简单，也更容易被桌面计算机实现。桌面客户端使用这些新协议之一，通过 TCP/ IP 直接与中间服务器通信，而中间服务器则实现了 X.500 DAP 。这两个小组都将他们的工作成果提交给了 IETF 。

桌面计算机的两种轻量级协议分别是 RFC 1202 中定义的目录辅助服务 ( DAS ) 和 RFC 1249 中定义的高效实现的 X.500 目录接口 ( DIXIE )。[ 图 1.11] 显示了使用 DIXIE 客户端/客户端/服务器架构的目录系统的架构。

![**图 1.11. DIXIE 为 X.500 目录提供前端**](./image/Chapter%201%20Directory%20Services%20Overview%20and%20History/01fig11.webp)

两种协议都取得了成功；不过， DIXIE 协议很快被采纳为访问 X.500 目录系统的首选方法。然而， DAS 和 DIXIE 协议的一个缺点是，它们都与单一的 X.500 实现（Quipu）紧密相关。

##### LDAP 的创建

在 DIXIE 和 DAS 证明了轻量级 X.500 访问协议的实用性之后， IETF 下属的 OSI -DS 工作组成员决定携手合作，为 X.500 目录开发一个功能齐全、轻量级的目录访问协议。由此， LDAP 诞生了。

第一个 LDAP 规范的开发者是 Wengyik Yeong、Steve Kille、Colin Robbins 和 Tim Howes（本书作者之一）。此外，互联网和 X.500 社区的许多人士也做出了贡献。第一个 LDAP 规范于 1993 年 7 月以 RFC 1487 的形式发布。第一个得到广泛应用的 LDAP 版本是版本 2 (LDAPv2)；LDAPv2 的最终规范以 RFC 1777 的形式发布。

##### LDAP 创新

LDAP 开发人员在四个重要方面简化了重量级的 X.500 DAP 协议：

1. 功能方面 ，LDAP 以更低的成本提供了 DAP 的大部分功能。它消除了 DAP 中冗余的操作和不常用的功能，简化了 LDAP 客户端和服务器的实现。
2. 数据表示 。 在 LDAP 中，大多数数据元素都以简单的文本字符串形式传输，从而简化了实现并提高了性能（但为了提高效率，文本字符串被封装在二进制编码的消息中）。
3. 传输方式方面 ， LDAP 直接运行在 TCP 协议之上，无需笨重的多层 OSI 网络协议栈。这简化了实现，提高了性能，并且消除了对 OSI 的需求，从而简化了 LDAP 目录的部署。

#### 早期 LDAP 实现

最初， LDAP 仅用于为基于 X.500 的目录服务提供前端。第一个 LDAP 实现是由作者在密歇根大学期间开发的。这个后来被称为 UM LDAP 的实现体积小、速度快，并且可以在各种流行的计算平台上运行。最重要的是，它包含一个简单且规范完善的 C 语言 API ，该 API 实现了 LDAP 的所有客户端功能，可用于开发任何类型的 LDAP 客户端应用程序。LDAPv2 客户端 API 最终成为事实上的标准，并在 RFC 1823 中发布。[ 图 1.12]展示了早期 UM LDAP 软件版本的组件。关键的服务器端组件是 ldapd，它是一个 LDAP 到 X.500 DAP 协议的转换器。

![**图 1.12. 早期 UM LDAP 版本的主要组成部分**](./image/Chapter%201%20Directory%20Services%20Overview%20and%20History/01fig12.webp)

密歇根大学 LDAP 实现的第一个版本于 1992 年在互联网上公开发布，并附带版权声明，允许不受限制地使用该软件。随后，大量免费和商业 LDAP 客户端软件相继问世，其中许多都基于密歇根大学的实现。

1995 年初，UM 的 LDAP 团队即将迎来又一次重大发现。在分析 UM 服务的目录访问统计数据时，他们注意到超过 99%的 X.500 目录访问都是通过 LDAP 进行的。这种情况在大多数 X.500 目录上都存在。[ 图 1.13] 展示了当时普遍存在的架构。

![**图 1.13. LDAP 目录系统架构，约 1995 年**](./image/Chapter%201%20Directory%20Services%20Overview%20and%20History/01fig13.webp)

尽管 LDAP 解决了目录客户端访问问题，但其服务器实现仍然庞大、复杂且难以部署。UM LDAP 团队意识到，通过移除中间的 ldapd 服务器，可以大幅降低系统的整体复杂性并显著提升性能。毕竟，ldapd 的所有时间都耗费在将 LDAP 请求转换为 DAP 请求，并将 X.500 服务器返回的 DAP 结果重新转换为 LDAP 结果上。

此外，构建全球互联的 X.500 目录的愿景似乎难以实现，因此人们开始质疑是否真的需要 X.500 目录服务器。于是，独立式或原生 LDAP 服务器的概念应运而生。这款新服务器被命名为 *slapd* （ *独立 LDAP 守护进程*的缩写），并在美国国家科学基金会的资助下迅速投入使用。[ 图 1.14]展示了修改后的 LDAP 系统架构。

![**图 1.14. 引入 slapd 后的 LDAP 系统架构**](./image/Chapter%201%20Directory%20Services%20Overview%20and%20History/01fig14.webp)

LDAP 在保留 X.500 模型最佳特性的同时，彻底摆脱了 X.500 的束缚，可以独立发展。与此同时，LDAPv2 协议新增了引用功能，作为一项实验性扩展，用于支持 slapd 目录服务器的互联网络。这些变化使 LDAP 不再仅仅是一个用于访问 X.500 目录的简单实用协议，而是发展成为构建完整目录服务的基础。首个包含 slapd 的 UM LDAP 软件版本是 1995 年 12 月发布的 UM LDAP 3.2。

#### LDAP 势头

LDAP 的商业成功在 1996 年 4 月得到保障，当时 Netscape 牵头联合 40 多家知名软件公司，共同认可 LDAP 作为首选的互联网目录服务协议。如今，Netscape、Sun Microsystems 和 Novell 等公司都开发了一套完整的基于 LDAP 目录服务的企业软件，所有主流网络应用软件供应商都在其客户端和服务器产品中支持 LDAP 。

#### LDAP Version 3 已开发

1997 年，随着 LDAP 协议第三版 (LDAPv3) 的发布， LDAP 的发展进入了一个更加成熟的阶段。当时就职于 Sun Microsystems 的 Mark Wahl，与一些 LDAP 的原始作者以及来自互联网的数百名人士共同参与了 LDAPv3 规范的制定。LDAPv3 在以下几个重要方面对 LDAPv2 进行了改进：

- *国际化* 。UTF -8（UCS 转换格式 8）字符集在所有适用的地方均被使用。由于 UTF-8 是通用 Unicode 字符集的编码，因此 LDAPv3 目录服务器和客户端可以存储和处理世界上所有语言中使用的所有字符。
- *引用*。 新增了一种将引用返回给其他服务器的标准机制，使得 LDAP 服务器能够像万维网服务器一样，以自下而上的方式进行部署。
- *安全性*。LDAP 增加了对简单身份验证和安全层 ( SASL ) 和传输层安全 ( TLS ) 的支持，以提高其安全性并支持更丰富的应用程序集。
- *可扩展性* 。LDAPv3可以扩展以支持新的操作，并且可以通过使用控件来扩展现有操作，从而允许 LDAP 逐步增强以满足未来的需求。
- *功能和模式发现* 。 所有 LDAPv3 服务器都会在一个名为*根 DSE* （ DSA 特定条目，或目录服务器特定条目）的特殊目录条目中发布它们支持的 LDAP 协议版本以及其他有用信息。此外，LDAPv3 服务器还会将其支持的目录模式作为一组 LDAP 属性发布。这些功能有助于 LDAP 客户端和服务器更智能地协同工作。

#### LDAP：协议还是目录服务？

有些人反对使用 “LDAP 目录*服务”* 这个术语。为什么呢？因为他们认为， LDAP 仅仅是一种目录访问协议，因此我们应该只讨论启用了 LDAP 的目录服务——例如，X.500 目录可以启用 LDAP ，Novell eDirectory 也启用了 LDAP 。那么，为什么本书通篇都使用 *“LDAP 目录服务”* 这个术语呢？

自从密歇根大学推出独立 LDAP 服务器 (slapd) 以及 IETF 发布 LDAPv3 规范以来，支持 LDAP 的目录服务器可以独立运行，无需依赖 X.500 标准的完整实现，也无需依赖除 LDAP RFC 和 LDAP 所依赖的 X.500 部分之外的任何其他目录规范。此外， LDAP 一词也已广泛用于指代服务器；例如，人们经常说“ LDAP 服务器”，就像说“ FTP 服务器”一样。因此，基于 LDAP 服务器集合的目录服务自然而然地被称为 *LDAP 目录服务* 。事实上，我们找不到比这更好的术语来描述像密歇根大学和 Netscape 开创的那种纯粹的 LDAP 解决方案了！

#### LDAP 的主要优势

如今， LDAP 显然已成为在线目录服务领域的主流， 人们正投入大量精力和热情开发和部署 LDAP 目录。LDAP 之所以能够脱颖而出，主导目录服务领域并吸引信息技术专业人士的关注，主要归功于以下几个因素：

- *LDAP 简单易用，功能强大*。 它支持各种各样基于目录的应用程序，这些应用程序的需求千差万别。
- *LDAP 无处不在* 。 密歇根大学的研究人员开发了一个优秀的 LDAP 实现，并将其免费发布在互联网上，这为 LDAP 的早期发展提供了强大的动力。如今，几乎所有主流和大多数非主流计算平台都提供了 LDAP 实现。
- *LDAP 目录价格低廉且易于理解* 。选择 LDAP 目录的组织会发现，它们的部署和维护成本相对较低 。LDAP 目录系统足够简单，无需大量顾问即可理解和部署。
- *LDAP目录服务性能更佳* 。LDAP目录产品的高可靠性、高性能和可扩展性，加上其通用设计，使其能够满足最重要的目录服务需求。
- *LDAP 拥有极高的“用户认知度”* 。在 Netscape 和其他数十家软件公司响应客户需求并支持 LDAP 后不久，人们对 LDAP 的兴趣便呈爆炸式增长。LDAP 正在满足人们对单一目录标准的渴望，并且这种势头仍在持续。

### 什么是 LDAP ？

如今， LDAP 一词指的是以下几种情况：

- 轻量级目录访问协议（Lightweight Directory Access Protocol，简称 LDAP）是一种标准的、可扩展的互联网协议，用于访问目录服务。

- 目录使用过程由四大模型作为指导：

  - **信息模型（information model）**：描述可以存入目录的数据内容；

  - **命名模型（naming model）**：描述如何组织目录数据、以及引用目录数据的方式；

  - **功能模型（functional model）**：描述你可以对目录数据执行哪些操作；

  - **安全模型（security model）**：描述如何保护目录数据，防止未授权访问。

- LDAP 数据交换格式 ( LDIF ) 是一种用于交换目录数据的标准文本格式。
- LDAP 服务器软件，包括商业和开源实现
- 一组通常与 LDAP 服务器和基于 LDAP 的应用程序捆绑在一起的命令行实用程序。
- LDAP 应用程序编程接口（API）用于开发 LDAP 客户端应用程序

### LDAP 协议

本节将讨论 LDAP 协议的各个操作，并展示客户端如何使用它们来执行各种实用任务。我们还将通过讨论网络传输协议来展示 LDAP 在网络上的工作原理。

需要注意的是， **LDAP 协议是一种*面向消息的*协议。客户端构建一个包含请求的 LDAP 消息并将其发送给服务器。服务器处理该请求，并将处理结果以一条或多条 LDAP 消息的形式发送回客户端。**

例如，当 LDAP 客户端在目录中搜索特定条目时，它会向服务器发送 LDAP 搜索请求消息。该消息包含一个由客户端生成的唯一消息 ID。服务器从其数据库中检索该条目，并通过 LDAP 消息将其发送给客户端。同时，服务器还会通过单独的 LDAP 消息向客户端返回结果代码。服务器发送给客户端的所有响应都使用客户端原始请求中提供的消息 ID 进行标识。[ 图 2.1]展示了这种交互过程。

![**图 2.1. 客户端从目录中检索单个条目**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig01.webp)

如果客户端搜索目录并找到多个条目，这些条目将以一系列 LDAP 消息的形式发送给客户端，每个条目对应一条消息。每个条目都有一个称为**可分辨名称 ( DN )** 的唯一名称，该名称以文本字符串的形式包含在 LDAP 消息中。构成搜索结果的条目以结果消息结尾，该结果消息包含搜索操作的总体结果， 如图 2.2 所示。

![图 2.2. 客户端从目录中检索多个条目](./image/Chapter%202%20Introduction%20to%20LDAP/02fig02.webp)

由于 LDAP 协议基于消息，因此它允许客户端同时发出多个请求。例如，客户端可以同时发出两个搜索请求。客户端会为每个请求生成一个唯一的消息 ID；特定请求的返回结果会带有该请求的消息 ID 标记，这使得客户端能够区分来自不同请求的多个响应，无论这些响应是乱序到达还是同时到达。

在[图 2.3]中，客户端同时发出两个搜索请求。服务器处理这两个操作并将结果返回给客户端 。 请注意，服务器在发送消息 1 的最终结果代码之前，先将消息 2 的最终结果代码（图中标记为 msgid=2 发送给了客户端。这完全符合规范。LDAP SDK （软件开发工具包）对程序员隐藏了这些细节。编写 LDAP 应用程序的程序员无需关心如何处理这些结果；SDK 会自动处理这些工作。

![**图 2.3. 客户端同时发出多个 LDAP 搜索请求**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig03.webp)

允许多个并发请求“同时进行”使得 LDAP 比那些以“同步”方式运行的协议（例如超文本传输协议，即 HTTP ）更加灵活高效。在同步协议中，服务器必须先响应每个客户端请求，才能发送下一个请求。例如，一个 HTTP 客户端程序（例如想要同时下载多个文件的 Web 浏览器）必须为每个文件打开一个连接。而 LDAP 则可以在单个连接上管理多个操作，从而减少服务器必须能够处理的最大并发连接数。

#### LDAP 协议操作

LDAP 有九种基本协议操作，可以分为三类：

1. 查询操作：搜索、比较。这两个操作允许您向目录提出问题。
2. 更新操作：添加、删除、修改、修改 DN （重命名）。这些操作允许您更新目录中的信息。
3. 身份验证和控制操作：绑定、解绑、放弃。绑定操作允许客户端通过提供身份和身份验证凭据向目录进行身份验证；解绑操作允许客户端终止会话；放弃操作允许客户端表明它不再对先前提交的操作结果感兴趣。

一个典型的完整的 LDAP 客户端/服务器 信息交换过程可能[如图 2.4] 所示，图中显示了 LDAP 客户端和服务器执行以下步骤：

![**图 2.4. 典型的 LDAP 交换**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig04.webp)

1. 客户端打开与 LDAP 服务器的 TCP 连接并提交绑定操作。此绑定操作包含客户端要进行身份验证的目录条目名称，以及用于身份验证的凭据。凭据通常是简单的密码，但也可能是用于验证客户端身份的数字证书。
2. 目录验证绑定凭据（检查密码或数字证书是否正确）后，会向客户端返回成功结果。
3. 客户端发出搜索请求。
4. 服务器处理此请求，结果得到两个匹配的条目。
5. 服务器发送结果消息。
6. 然后客户端发出一个解除绑定请求，向服务器表明客户端想要断开连接。
7. 服务器响应，关闭了连接。

#### LDAP 可扩展性

除了提供九种基本协议操作外，LDAPv3 还设计为可通过三种方式进行扩展：

1. LDAP 扩展操作。这些全新的协议操作可以通过 LDAPv3 扩展操作来定义。如果需要新的操作，可以对其进行定义并将其标准化，而无需修改 LDAP 核心协议。扩展操作的一个示例是 StartTLS，它向服务器指示客户端希望开始使用传输层安全协议 ( TLS ) 来加密连接，并可选择进行身份验证。
2. LDAP 控制。这些额外的信息附加在现有的 LDAP 操作之上，用于改变操作的行为。例如，当客户端想要操作存储在目录中的某些类型的元信息时（这些元信息通常对目录用户隐藏）， `ManageDSAIT` 控制会随修改操作一起发送。未来，可能会定义更多控制，以更有效地改变现有 LDAP 操作的行为。
3. 简单认证和安全层 ( SASL ) 是一个支持多种认证方式的框架。如果使用 SASL 框架实现认证，则可以轻松调整 LDAP 以支持新的、更强大的认证方式。SASL 还支持客户端和服务器协商底层安全机制的框架，例如对所有客户端/服务器流量进行加密。不过，SASL 并非 LDAP 特有 ； 其通用框架可以适用于各种互联网协议。

### 网络传输中的 LDAP 协议

LDAP 客户端和服务器之间来回传输哪些信息？本书并非探讨协议设计，因此我们在此不做过多赘述，但关于 LDAP 网络协议，您应该了解一些基本知识。

LDAP 使用简化版的*基本编码规则* ( BER )。BER 是一套用于以系统无关且紧凑的方式编码各种数据类型（例如整数和字符串）的规则 。BER 还定义了将这些基本数据类型组合成诸如集合和序列等有用结构的方法。LDAP 使用的简化版 BER 通常被称为*轻量级 BER* ( LBER ) 。LBER 摒弃了 BER 可以表示的许多较为深奥的数据类型，从而简化了实现。

由于 LDAP 使用 LBER ，它并非像 HTTP 那样简单的基于文本的协议，因此您无法直接通过 Telnet 连接到服务器上的 LDAP 端口并开始输入命令。此外，如果您想使用网络嗅探程序来观察客户端和服务器之间的 LDAP 通信，该程序必须能够理解 LDAP 协议才能正常工作（大多数先进的嗅探软件都支持 LDAP 协议——例如，知名的开源嗅探器 Ethereal 就有一个 LDAP 模块）。如果您熟悉基于文本的互联网协议，例如邮局协议 ( POP )、互联网消息访问协议 ( IMAP ) 和简单邮件传输协议 ( SMTP )，那么这可能看起来是一个令人遗憾的限制。另一方面，域名系统 ( DNS ) 作为一个成功的分布式系统，使用的协议包含非文本协议原语 。DNS 和 LDAP 都有通用的客户端库实现，这使得这种限制的影响相对较小。

### LDAP 模型

LDAP 定义了四个基本模型，完整地描述了它的运行方式、 LDAP 目录中可以存储哪些数据以及可以用这些数据做什么。

#### LDAP 信息模型

LDAP 信息模型 定义了可存储在目录中的数据类型与信息基本单元。换句话说，LDAP 信息模型描述了用于构建目录的基础组件。

##### 条目、属性和值

目录中的**信息基本单元是条目（entry）**，**条目是某一个对象的一组信息集合**。条**目内的信息通常用来描述现实世界中的对象**，例如人员，但该模型并**不强制要求**必须如此。 在典型目录中，会有成千上万个条目，分别对应该目录所服务组织内的人员、部门、服务器、打印机以及其他现实实体。图示展示了一套典型目录的局部，其中包含与组织中一些现实世界对象相对应的条目。

![Part of a Typical Directory](./image/Chapter%202%20Introduction%20to%20LDAP/02fig07.webp)

每一条目录条目都拥有一个**可分辨名称（DN）**。例如，上图示组织对象，它的 DN 为 dc=example,dc=com。本章后续深入讲解 LDAP 命名模型时，会对 DN 展开详细讨论。

一条条目由**一组属性（attributes）**构成，每一个属性描述对象的某一项特征。每个属性包含**属性类型**以及一个或多个**属性值**：属性类型定义该属性存储哪一类信息，属性值保存实际的数据内容。

下图一条人员条目，包含全名、姓氏、电话号码、电子邮件地址等属性。

![图 2.8. 显示属性类型和值的目录条目](./image/Chapter%202%20Introduction%20to%20LDAP/02fig08.webp)

属性类型也具有关联的*语法*和一组*匹配规则* 。属性的语法指定了该类型属性中可以存在的数据的格式。例如， `INTEGER` 语法只允许值中包含数字。匹配规则指定以下内容：

- 用于比较值是否等效的规则。例如， `caseIgnoreMatch` 规则指定在搜索或替换值时忽略大小写。在比较值 `Smith` 和 `smith` 时，如果使用 `caseIgnoreMatch` 匹配规则，则它们被视为等效。
- 用于对值进行排序的规则。例如， `caseIgnoreMatch` 规则指定值按字典顺序排序，而 `integerMatch` 规则指定值按其数值排序。

属性大致分为两大类：**用户属性（user attributes）**与**操作属性（operational attributes）**。 用户属性是条目里的 “普通” 属性，目录使用者在拥有对应权限时可以对其进行修改。 操作属性属于特殊属性，要么用于控制目录服务器的运行行为，要么用于反映目录的运行状态。`modifyTimeStamp`（修改时间戳）就是一个操作属性示例：它记录条目最后一次被修改的时间，由目录自动维护。当向客户端返回条目数据时，**默认不会包含操作属性**，除非客户端显式按名称请求获取。

属性值还可以附加其他约束。某些服务器软件允许管理员声明特定属性类型是否可以包含多个值，或者是否只能存储单个属性值。例如， `givenName` 属性通常是多值的，以便一个人可以拥有多个名字（例如， Jim 和 James ）。另一方面，存储员工 ID 号的属性通常是单值的。某些服务器软件允许管理员设置属性值的最大长度。此功能可用于防止目录用户占用过多的存储空间。



##### 维持数据秩序：目录模式（Schema）

目录中的每个条目都有一组**必需的属性类型（required attribute types）**和一组**允许的属性类型（allowed attribute types）**。例如，描述人物的条目必须包含 `cn` （common name）属性和 `sn` （surname）属性。其他属性对于人物条目是允许的，但并非必需。任何未明确指定为必需或允许的属性类型均被禁止。**所有关于必需属性和允许属性的信息集合称为*目录模式* 。**

需要注意的是，目录模式与 LDAP 目录树中条目的排列方式无关。如果您熟悉关系数据库技术，这一点可能会让您感到奇怪，因为在关系数据库技术中， *“模式”* 是一个更全面的术语，用于描述数据库表的布局及其相互关系。**LDAP 模式的概念则更为简单，因此它仅决定单个条目中包含哪些类型的数据。**

总而言之，LDAP 信息模型描述的是 **条目（entries）**，它们是目录的基本组成单位。条目由**属性（attributes）**组成，而属性由一个**属性类型（attribute type）**和一个或多个**属性值（values）**组成。

属性可以具有相应的约束，用于限制属性值中数据的**类型和长度**。目录 **Schema（模式）**则规定了一个条目中**必须包含或允许包含哪些属性类型**。

#### LDAP 命名模型

LDAP **命名模型（naming model）**定义了如何组织和引用目录中的数据。换句话说，它描述了如何利用作为基本构建单元的**目录条目（directory entries）**构建不同类型的结构。

当你将这些条目组织成一个逻辑结构后，命名模型还规定了如何在该结构中**引用某个特定的目录条目**。

LDAP 命名模型所提供的灵活性，使你能够按照便于管理的方式将数据组织到目录中。例如，你可以创建一个容器，用于存放组织中所有描述人员的条目，再创建另一个容器，用于存放所有组的条目。

或者，你也可以按照组织各办公地点的地理分布来组织目录结构。

LDAP 命名模型规定，目录中的条目应按照**倒置树（inverted tree）结构**进行组织，如图 2.9 所示。

熟悉 Unix 系统层次化文件系统的读者会发现，这种目录结构与 Unix 文件系统具有相似之处。Unix 文件系统由一组目录和文件组成；每个目录下面可以包含零个或多个文件或子目录。

![**目录树**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig09.webp)

![**图 2.10. 典型的 Unix 文件系统的一部分**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig10.webp)

Unix 文件系统层次结构和 LDAP 目录层次结构之间存在三个显著差异。首先， **LDAP 模型中实际上没有根条目**。文件系统当然有一个根目录，它是文件系统层次结构中所有文件或目录的共同祖先。而 **LDAP 目录层次结构中的根条目则是一个特殊条目，它包含目录服务器的配置信息，通常不用于存储实际信息**。

第二个主要区别在于，在 LDAP 目录中，**每个节点都包含数据，并且任何节点都可以作为容器**。这意味着任何 LDAP 条目都可以在其下包含子节点。相比之下，在文件系统中，一个节点要么是文件，要么是目录，二者不能同时存在。只有目录可以包含子节点，而只有文件可以包含数据。换一种方式理解：目录中的一个条目可以**同时承担类似文件和目录的角色**。图 2.11 所示的 LDAP 目录树展示了这一概念。可以看到，`dc=example`、`dc=com`、`ou=People` 和 `ou=Devices` 这些条目都包含数据（属性），同时又作为容器，在其下包含子节点。

![**图 2.11. 典型 LDAP 目录的一部分**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig11.webp)

文件系统层次结构和 LDAP 层次结构的第三个也是最后一个区别在于树中各个节点的命名方式。LDAP 名称相对于文件系统名称是反向的。例如，请看图 2.10 和图 2.11 中带阴影的节点名称。在图 2.10 中，带阴影的节点是一个文件，其完整文件名为 ==/usr/bin/grep== 。请注意，如果从左到右读取文件名，则会从树的顶部（ ==/== ）向下移动到所指定的文件。

将此名称与图 2.11 中带阴影的目录项名称进行对比： ==uid=bjensen,ou=people,dc=example,dc=com== 。请注意，如果从左到右阅读，您会从被命名的特定条目向上移动到树的顶部。

尽管 LDAP 支持以层次结构来组织目录项，但它并不强制规定任何特定的层次结构。就像你可以按照对自己来说合理且便于管理的方式来组织文件系统一样，你也可以按照自己的需要构建任意形式的目录层次结构。

除了规定如何将目录条目组织为层级结构之外，LDAP 命名模型还定义了如何引用目录中的单个条目。我们在讨论文件系统层级与 LDAP 目录层级的异同之处时，已经简要提及这一点。现在我们来深入讲解命名相关内容。

##### DN & RDN

我们需要一种命名模型，以便为目录中的每个条目指定唯一的名称，从而能够明确地引用任何条目。在 LDAP 中，我们使用**可分辨名称 (DN)** 来引用条目。

与文件系统的路径名类似，我们通过依次连接一个 LDAP 条目的所有父级条目的名称，一直追溯到根节点，从而构成该 LDAP 条目的名称。

例如，回顾图 2.11 所示的目录树。图中阴影条目的名称是：

```
uid=bjensen,ou=people,dc=example,dc=com
```

从左向右读取这个名称时，你可以沿着这条路径，从该条目本身一直追溯到目录树的根节点。名称中的各个组成部分使用逗号分隔。逗号后的空格是可选的，因此下面两个可分辨名称是等价的：

```
uid=bjensen, ou=people, dc=example, dc=com
uid=bjensen,ou=people,dc=example,dc=com
```

在任何条目的 DN 中，最左侧的组成部分称为**相对可分辨名称（RDN）**。对于一组同级条目（即拥有相同直接父条目的条目），每个 RDN 都必须是唯一的。

将这一规则递归地应用于整个目录树，就可以确保不存在两个拥有相同 DN 的条目。

如果你尝试添加两个名称相同的条目，目录服务器会拒绝添加第二个条目的请求。这类似于 Unix 或 Microsoft Windows 文件系统：如果某个目录中已经存在一个文件，你不能在同一个目录中再创建一个同名文件。

只有当 RDN 拥有共同的直接父级时，它们才需要是唯一的。请看图 2.12 中的树状图。即使有两个条目都包含 RDN ==cn=John Smith== ，它们也位于不同的子树中，因此该树状图完全合法。

![**图 2.12. 如果条目位于树的不同部分，则允许它们具有相同的 RDN。**](./image/Chapter%202%20Introduction%20to%20LDAP/02fig12.webp)

##### 多值 RDN

您可能已经注意到，我们展示的每个 RDN 都由两部分组成：属性名称和值，两者之间用等号 ( `=` ) 分隔。一个 RDN 也可以包含多个这样的名称-值对。这种结构称为*多值 RDN* ，如下所示：

```
cn=John Smith + mail=jsmith@example.com
```

此条目的 RDN 由两个 ==attribute=value== 对组成： ==cn=John Smith== 和 ==mail=jsmith@example.com== 。

多值 RDN 可用于区分原本相同的 RDN。例如，如果同一个容器中有多个 John Smith 条目，则可以使用多值 RDN 为每个条目分配唯一的 RDN。但是，通常应避免使用多值 RDN，原因有二：首先，它们往往会使命名空间变得混乱，而且有更好的方法可以为条目生成唯一名称。根据 LDAP 所依据的 X.500 规范，多值 RDN 中的值是一个集合，这意味着顺序并不重要。因此，以下两个 DN 指向同一个条目：

```
cn=John Smith + mail=jsmith@example.com, dc=example, dc=com
mail=jsmith@example.com + cn=John Smith, dc=example, dc=com
```



##### 转义

当某些字符出现在 DN 的组成部分中时，必须进行转义。例如，如果您的目录中有条目 `o=United Widgets,Ltd.` 该如何处理？逗号是组织名称的一部分，而不是 DN 组成部分之间的分隔符。为了消除歧义，您必须使用反斜杠 ( `\` ) 转义所有字面逗号（即 RDN 中的逗号）。因此，在我们的示例中， DN 应为：

| 字符 (Character)                       | 十进制码 (Decimal Value) | 转义序列 (Escape Sequence) |
| -------------------------------------- | ------------------------ | -------------------------- |
| DN 或 RDN 开头 / 末尾处的空格（Space） | 32                       | `\ `（反斜杠 + 空格）      |
| DN 或 RDN 开头的井号（#，Octothorp）   | 35                       | `\#`                       |
| 逗号（,）                              | 44                       | `\,`                       |
| 加号（+）                              | 43                       | `\+`                       |
| 双引号（"）                            | 34                       | `\"`                       |
| 反斜杠（\）                            | 92                       | `\\`                       |
| 小于号（<）                            | 60                       | `\<`                       |
| 大于号（>）                            | 62                       | `\>`                       |
| 分号（;）                              | 59                       | `\;`                       |

#### LDAP 功能模型

现在您已经了解了 LDAP 信息和命名模型，接下来需要一种方法来访问存储在目录树中的数据 。LDAP 功能模型描述了您可以使用 LDAP 协议对目录执行的操作。

LDAP 功能模型由一系列操作组成，这些操作分为三组。 

1. *查询操作*允许您搜索目录并检索目录数据。 
2. *更新操作*允许您添加、删除、重命名和更改目录条目。 
3. *身份验证和控制操作*允许客户端向目录验证自身身份并控制会话的某些方面。

除了这三大类操作之外， LDAP 协议版本 3 还定义了一个框架，允许通过 *LDAP 扩展操作*向协议中添加新操作。扩展操作使得协议能够以有序的方式进行扩展，从而满足不断涌现的新市场需求。扩展操作已在前面的 “LDAP 可扩展性”一节中进行了描述。

##### LDAP 查询操作

LDAP 的两种查询操作允许 LDAP 客户端搜索目录并检索目录数据。

1. 搜索操作允许客户端在目录中查找条目，
2. 比较操作允许客户端测试条目是否包含特定属性值。

###### LDAP 搜索操作

LDAP 搜索操作用于在目录中搜索条目并检索单个目录条目。LDAP 没有读取操作。要读取特定条目，必须使用一种搜索操作形式，将搜索范围限定为要检索的条目。本章稍后将讨论如何搜索目录并检索特定条目，以及如何列出树中特定位置的所有条目。

LDAP 搜索操作需要八个参数：

1. **Base object for the search**：搜索基准对象
2. **Search scope**：搜索范围
3. **Alias dereferencing options**：别名解引用选项
4. **Size limit**：大小限制
5. **Time limit**：时间限制
6. **Attributes-only parameter**：仅返回属性类型参数
7. **Search filter**：搜索过滤器
8. **List of attributes to return**：待返回属性列表

####### 基准对象

第一个参数是搜索的**基准条目（base entry）**，其中 *entry* 和 *object* 两个术语可以互换使用。该参数以 **DN** 表示，用于指定**搜索的起始条目**。

####### 搜索范围

第二个参数是**搜索范围（scope）**。搜索范围有三种类型。

1. `sub`（subtree，子树）表示从基准条目开始，向下搜索整个子树，一直到树的叶节点。
2. `onelevel` 表示只搜索**基准条目的直接子条目**，不继续搜索更深层次的后代条目。
3. `base` 表示将搜索范围限制在**基准条目本身**；这种范围用于从目录中获取某一个特定条目。

图 2.14 展示了这三种搜索范围。**基准条目（base object）与搜索范围（search scope）共同确定了要搜索的目录树区域。**

![The Three Types of Search Scope](./image/Chapter%202%20Introduction%20to%20LDAP/02fig14.webp)

####### 别名解引用选项

第三个搜索参数 `derefAliases` 告诉服务器在执行搜索时是否应该取消对别名的引用。此参数有四个可能的值：

1. **`neverDerefAliases` 。** 在搜索或定位搜索的基本对象时，不要取消对别名的引用。
2. **`derefInSearching` 。** 在搜索基本对象的子对象时取消引用别名，但不在定位搜索的基本对象时取消引用别名。
3. **`derefFindingBaseObject` 。** 取消对查找搜索的基本对象时使用的别名的引用，但不取消对搜索基本对象的子对象的引用。
4. **`derefAlways` 。** 在搜索基本对象的下级对象和定位搜索的基本对象时，都会取消引用别名。

####### 尺寸限制

第四个搜索参数是大小限制。此参数告诉服务器客户端只希望接收特定数量的条目。例如，如果客户端设置的大小限制为 100，但服务器找到了 500 个匹配条目，则只会向客户端返回前 100 个条目，并返回 `LDAP_SIZELIMIT_ EXCEEDED` 的结果代码。大小限制为 0 表示客户端希望接收所有匹配条目。（请注意，服务器可能会设置最大大小限制，非特权客户端无法覆盖此限制。）

####### 时限

第五个搜索参数是时间限制。此参数告诉服务器尝试处理搜索请求的最长时间（以秒为单位）。如果超过时间限制，服务器将停止处理请求，并向客户端发送 `LDAP_TIMELIMIT_EXCEEDED` 结果代码。时间限制为 0 表示不设置任何限制。（请注意，服务器可能会设置一个非特权客户端无法覆盖的最大时间限制。）

####### 仅属性参数

第六个搜索参数 `attrsOnly` 是一个布尔参数。如果设置为 `true` ，服务器将仅向客户端发送属性类型，而不会发送属性值。如果客户端只想了解条目包含哪些属性，而不需要接收实际值，则可以使用此参数。如果此参数设置为 `false` ，则会返回属性类型和值。

####### 搜索筛选器

第七个搜索参数是搜索过滤器，它是一个描述要返回的条目类型的表达式。LDAP 搜索操作中使用的过滤器表达式非常灵活；下一节 “LDAP 搜索过滤器”将详细讨论它们。

####### 要返回的属性列表

第八个也是最后一个搜索参数是每个匹配条目要返回的属性列表。如果此列表为空，则返回所有用户属性。特殊值 `*` 也表示返回所有用户属性，但它允许您指定要返回的其他非用户（操作）属性。（如果没有此特殊值，则无法请求所有用户属性以及一些操作属性。）

有时，您可能只想验证某个条目是否存在，但并不需要检索任何属性。如果您不想检索任何属性，则应指定属性名称 `1.1` 。 表 2.2 提供了一些属性列表示例以及服务器返回的相应属性。

>
> 熟悉 ldapsearch 命令行实用程序的读者会注意到，并非必须提供刚才讨论的所有搜索参数。原因是 ldapsearch 实用程序为除基本对象和搜索过滤器之外的所有选项都提供了默认值。

###### LDAP 搜索过滤器

LDAP 过滤器（LDAP filter）是由多个**属性—值断言（attribute–value assertion）**按照布尔逻辑组合而成的。

一个属性—值断言由两部分组成：**属性名称（attribute name）*和*值断言（value assertion）**。可以把值断言理解为一个允许使用通配符的值。

下面几节将介绍各种类型的搜索过滤器。我们使用 RFC 2254 定义的 LDAP 搜索过滤器表示法。这种表示法很方便，因为过滤器可以编码为文本字符串。（在 LDAP 协议内部，过滤器实际上使用 **BER** 进行编码，前文已经讨论过这一点。）这种表示法也是使用 `ldapsearch` 命令行工具时所采用的格式，本章后面会介绍该工具。

####### 等值过滤器

*等值过滤器*允许您查找与特定值完全匹配的条目。例如：

```
(sn=smith)
```

此过滤器匹配 ==sn==（surname，姓氏）属性值恰好为 ==smith== 的条目。由于 ==sn== 属性所关联的相等匹配规则（equality matching rule）是 caseIgnoreMatch，因此在查找匹配条目时，属性值和过滤器中的值**不区分大小写**。

####### 子字符串过滤器

在过滤器中使用通配符时，它们被称为*子字符串过滤器* 。例如，过滤器

```
(sn=smith*)
```

会匹配所有 ==sn== 属性值以“smith”开头的条目。姓氏为 Smith 、 Smithers 、 Smithsonian 等的条目都将被返回。

通配符可以出现在筛选表达式中的任何位置，因此筛选条件 `(sn=*smith)` 会匹配姓氏以“smith”结尾的条目（例如， `Blacksmith` ）。筛选条件 `(sn=smi*th)` 会匹配姓氏以“smi”开头并以“th”结尾的条目，而筛选条件 `(sn=*smith*)` 会匹配姓氏属性中包含字符串“smith”的条目。请注意，通配符可以匹配零个或多个任意字符，因此筛选条件 ( `sn=*smith*` ) 会匹配姓氏为 Smith 的条目，以及所有包含字符串“smith”的姓氏条目。

####### 近似过滤器

除了相等性和子字符串过滤器之外，服务器还支持*近似过滤器* 。例如，在大多数目录服务器上，过滤器 `(sn~=jensen)` 会返回姓氏属性值听起来像“jensen”（例如 `jenson` ）的条目。服务器如何实现此过滤器取决于各个供应商以及服务器支持的语言。

####### “大于等于”和“小于等于”筛选器

LDAP 服务器还支持对具有固有顺序的属性使用“大于等于”和“小于等于”过滤器。例如，过滤器 `(sn<=Smith)` 将返回姓氏在字典序上小于或等于 `Smith` 所有条目。所使用的顺序取决于与特定属性关联的匹配规则。使用 `caseIgnoreOrderingMatch` 匹配规则定义的 `sn` 属性按字典序排序，不区分大小写。具有 `INTEGER` 语法的属性将使用按数值排序的匹配规则进行定义。没有固有顺序的属性（例如 JPEG 照片）无法使用此类过滤器进行搜索。

如果你需要**大于**或者**小于**过滤器（不带等于的形式），请注意：**大于**是**小于或等于**的补集；**小于**是**大于或等于**的补集。换句话说，`(age>21)` 并不是合法的 LDAP 过滤器，它等价于 `(!(age<=21))`。同理，`(age<21)` 同样不是合法 LDAP 过滤器，等价于 `(!(age>=21))`。

在这些情况下， `!` 是否定运算符

####### 存在过滤器

另一种搜索过滤器是*存在性过滤器* 。它匹配属性至少包含一个值的任何条目。例如，筛选器 `(telephoneNumber=*)` 匹配所有包含电话号码的条目。

####### 可扩展匹配过滤器

最后一类搜索过滤器是**可扩展匹配过滤器**，该过滤器仅受 LDAPv3 服务器支持。可扩展匹配过滤器的作用是允许服务器实现新的匹配规则，并供客户端调用使用。回顾前面讲到的 `caseIgnoreMatch`（忽略大小写匹配）规则示例：每一条匹配规则都自带一套值比较逻辑，这套逻辑决定做值比对时是否区分大小写。当定义新的属性类型时，可能也需要定义全新的值比较方式。可扩展匹配还支持定义面向特定语言的匹配规则，让非英语语种的值也能够得到合理比对。

它还有一个额外优势：可扩展匹配可以指定对条目 DN 内部所包含的属性进行搜索。举个例子，借助可扩展匹配，你可以查找目录中**DN 任意位置包含 `ou=Engineering` 这一属性‑值断言**的全部条目。如果没有可扩展匹配功能，则无法针对 DN 的各个组成部分进行检索。

可扩展匹配过滤器的语法相对复杂，一共由五部分构成，其中三部分为可选项：

1. 属性名：如果省略，则会使用所有支持该匹配规则的属性类型与目标值做比对。
2. 可选字符串`:dn`：表示在搜索过程中，把构成条目 DN 的各个属性当作该条目自身的普通属性参与匹配。
3. 可选的冒号加匹配规则标识符：用于指定要使用的具体匹配规则。若未提供匹配规则，则使用待检索属性的默认匹配规则；**如果省略属性名，则必须提供冒号与匹配规则**。
4. 固定字面串 `:=`：用于分隔匹配规则标识符和属性值。
5. 用于比对的属性值。

可扩展搜索过滤器的形式化语法：

```
attr [":dn"] [":" matchingrule] ":=" value
```

其中：

- `attr` 为属性名。
- `matchingrule` 一般使用对象标识符（OID）表示；如果该匹配规则配置了描述性名称，也可以直接使用名称。你的目录服务器所支持匹配规则的 OID 可查阅服务器文档。
- `value` 是参与比对的属性值。

尽管 LDAP 在很大程度上不再强制要求使用 OID，但你还是会不时见到它，尤其是在使用可扩展匹配规则，或是自定义扩展目录模式的时候。

下面来看几组可扩展匹配过滤器示例：

下面这条过滤器要求返回所有`cn`属性匹配`Barbara Jensen`的条目： 

```
(cn:1.2.3.4.5.6:=Barbara Jensen)
```

进行值比对时，将使用 OID 为`1.2.3.4.5.6`对应的匹配规则。

下面这条过滤器要求返回姓氏（sn）中包含字符串`jensen`的所有条目：

```
 (sn:dn:1.2.3.4.5.7:=jensen)
```

####### 否定运算符

如果筛选条件前面加上感叹号（ `!` ），则可以否定任何搜索元素。例如，筛选条件 `(!(sn=Smith))` 会匹配所有 `sn` 属性值不为 `smith` 条目，包括根本没有 `sn` 属性的条目。

####### 过滤器条件的组合

过滤器还可以通过 AND 和 OR 运算符组合。AND 运算符用 `&` 符号表示，OR 运算符用竖线 `|` 表示。组合搜索过滤器时，使用*前缀表示法* ，其中运算符位于其参数之前。

我们来看一些 LDAP 搜索过滤器的组合示例。过滤器 `(&(sn=Smith) (L=Mountain View))` 匹配所有姓氏为 `smith` 且 `L` （地点）属性为 `Mountain View` 的条目。换句话说，此过滤器查找所有居住在 Mountain View 且姓氏为 Smith 的人。过滤器 `(|(sn=Smith) (sn=Jones))` 匹配所有姓氏为 `Smith` 或 `Jones` 的人。

使用括号可以将更复杂的筛选条件分组，使筛选条件的含义更加明确。例如，如果您想在目录中搜索所有包含电子邮件地址但没有电话号码的条目，则可以使用以下筛选条件：

```
(&(mail=*)(!(telephoneNumber=*)))
```

请注意，括号将否定运算符与电话号码的存在过滤器绑定在一起。

严格来说，即使筛选条件只包含一个词条，也始终需要括号。某些 LDAP 软件允许您省略括号，并在向服务器发送搜索请求之前自动添加。但是，如果您使用现有的 SDK 开发自己的软件，则必须包含括号。

####### 搜索过滤器中的转义

如果需要检索的属性值包含 5 种特定字符之一，就必须使用转义序列替换该字符；转义序列由**反斜杠**加上代表该字符编码的两位十六进制数构成。下表列出了必须转义的字符及其对应的转义序列。举个例子，若要查找`cn`属性精确等于`A*Star`的所有条目，过滤器写法为 `(cn=A\2AStar)`。

| 原字符 | 含义       | 转义序列 |
| ------ | ---------- | -------- |
| `*`    | 通配符     | `\2A`    |
| `(`    | 左括号     | `\28`    |
| `)`    | 右括号     | `\29`    |
| `\`    | 反斜杠本身 | `\5C`    |
| `\00`  | NUL 空字符 | `\00`    |

##### LDAP 更新操作

LDAP 有四种更新操作：添加、删除、重命名（修改 DN ）和修改。这四种操作定义了您可以操作目录中数据的方式。

###### 添加操作

添加操作允许您创建新的目录条目。它有两个参数：要创建的条目的专有名称，以及构成新条目的一组属性和属性值。要成功完成添加操作，必须满足以下四个条件：

1. 新条目的父条目必须已存在于目录中。
2. 不得出现同名条目。
3. 新条目必须符合现行的模式（schema）。
4. 访问控制必须允许该操作。

如果满足所有这些条件，则将新条目添加到目录中。

###### 删除操作

删除操作会从目录中移除一个条目。它只有一个参数：要删除的条目的 DN。要成功完成删除操作，必须满足以下三个条件：

1. 要删除的条目必须存在。
2. 要删除的条目不能包含子条目。
3. 访问控制必须允许删除条目。

如果满足所有这些条件，则从目录中删除该条目。

###### 重命名（修改 DN ）操作

重命名（或修改 DN ）操作用于重命名和/或移动目录中的条目。它有四个参数：要重命名的条目的 DN 、条目的新 RDN 、一个可选参数（指定条目的新父级）以及删除旧 RDN 标志。修改 DN 操作要成功，必须满足以下条件：

1. 要重命名的条目必须已存在。
2. 新条目的名称不得已被其他条目使用。
3. 访问控制必须允许该操作。

如果满足所有这些条件，则重命名和/或移动条目。

如果条目要重命名但仍保留相同的父条目，则 `new-parent` 参数留空。否则，`new-parent` 参数指定要将条目移动到的容器的 DN。`delete -old- RDN` 标志是一个布尔标志，用于指定是否保留条目的旧 RDN 作为条目的属性，还是将其删除。 图 2.16 至 2.20 显示了使用 `modify -DN` 操作可以执行的各种重命名和移动条目的组合。

###### 修改操作

修改操作允许您更新现有目录条目。它接受两个参数：要修改的条目的 DN 和要应用的一组修改。这些修改可以指定向条目添加新的属性值、从条目中删除特定的属性值，或者将给定属性的所有属性值替换为一组新的属性值。修改请求可以包含所需的任意数量的属性修改。

要使修改操作成功，必须满足以下条件：

1. 要修改的条目必须已存在。
2. 所有属性修改都必须成功。
3. 生成的条目必须符合当前生效的模式。
4. 访问控制必须允许更新。

最后一点引出了关于 LDAP 更新操作的另一个重要主题：每个操作都是*原子性的* ，这意味着整个操作作为一个单独的工作单元来处理。要么该单元完全成功，要么不执行任何修改。例如，一个影响条目中多个属性的修改请求不可能只成功一部分，即某些属性被更新而其他属性未被更新。如果客户端从服务器收到成功结果，则表示所有修改都已应用到该条目。如果服务器向客户端返回错误，则表示所有修改均未应用。

##### LDAP 身份验证和控制操作

LDAP 包含两种身份认证操作（绑定(bind)与解绑(unbind)），以及一种控制操作（放弃(abandon)）。

###### 绑定操作

客户端通过提供 DN 和一组凭据，可以使用绑定操作向目录进行身份验证。服务器会检查凭据是否与给定的DN 匹配，如果匹配，则记录客户端已通过身份验证，只要连接保持打开状态或客户端重新进行身份验证，该身份验证就一直有效。服务器可以根据客户端的身份授予其相应的权限。

绑定方法有多种类型。在简单绑定中，客户端以明文形式向 LDAP 服务器提供 DN 和密码。服务器验证该密码是否与条目 userPassword 属性中存储的密码值匹配，如果匹配，则向客户端返回成功代码。

简单的绑定操作会将密码以明文形式通过网络发送到服务器。但是，您可以使用安全套接字层 ( SSL ) 或传输层安全协议 (TLS) 对连接进行加密，以防止窃听者拦截密码。下一节 “LDAP 安全模型”将讨论 SSL 或 TLS 。

LDAPv3 还包含一种新的绑定操作类型： SASL 绑定。SASL 是一个可扩展的、协议无关的框架，用于执行身份验证和安全参数协商。使用 SASL 时，客户端指定要使用的身份验证协议类型。如果服务器支持该身份验证协议，则客户端和服务器将执行约定的协议。

例如，客户端可以指定使用 DIGEST-MD5 SASL 机制进行身份验证。如果服务器实现了 DIGEST-MD5（所有符合 LDAPv3 标准的服务器都必须实现），它会构建一个质询并将其发送给客户端。客户端计算对该质询的响应并将其发送给服务器，服务器验证该响应并将最终结果返回给客户端。如果正确实现，DIGEST-MD5 身份验证可以防止窃听。

将 SASL 合并到 LDAPv3 中意味着可以轻松地为 LDAP 实现新的身份验证方法，例如智能卡或生物特征身份验证，而无需修改协议。

客户端完全可以先执行一次绑定（bind），执行一些操作，然后再次执行绑定，再执行更多操作。如果这样做，那么客户端在重新绑定之后执行的所有操作，都会以**新的绑定身份**进行。如果一次绑定操作失败，那么该客户端会被视为处于**匿名绑定（anonymous bind）**状态。

在 Active Directory 服务接口（Active Directory Services Interface，ADSI）SDK 中，bind 一词的含义略有不同。使用 ADSI 绑定到某个目录条目时，你不仅是在向目录进行身份验证，同时还会将该条目设置为后续目录搜索的**基准对象（base object）**。

###### 解绑操作

第二个身份验证操作是解除绑定操作。解除绑定操作没有参数。当客户端发出解除绑定操作时，服务器会丢弃与客户端连接关联的所有身份验证信息，终止所有未完成的 LDAP 操作，并断开与客户端的连接，从而关闭 TCP 连接。

虽然客户端在断开连接前发出 unbind 操作被认为是一种良好的做法，但如果客户端在未解除绑定的情况下断开连接，服务器实现必须表现得正确。

###### 放弃操作

放弃操作只有一个参数：要放弃的 LDAP 操作的消息 ID。当客户端不再需要获取先前启动的操作的结果时，它会发出放弃操作。服务器收到放弃请求后，会终止处理与该消息 ID 对应的操作。放弃请求通常由 GUI 客户端使用，在用户取消长时间运行的搜索请求时发送。

请注意，客户端发出的放弃请求和服务器发送给客户端的已放弃操作的结果可能会在传输过程中相互干扰。客户端需要做好准备，接收（并丢弃）服务器仍然发送的、客户端已放弃的操作结果。但是，如果您使用的是 LDAP SDK ，则无需担心这个问题； SDK 会自动处理这些繁琐的工作。

#### LDAP 安全模型

我们目前已经讨论了四种 LDAP 模型中的三种。我们有一组目录条目，它们排列成一个层级结构，还有一组协议操作，允许我们对目录进行身份验证、搜索和更新。剩下的就是提供一个框架，用于保护目录中的信息免受未经授权的访问。这就是 LDAP 安全模型的目的。

该安全模型基于 LDAP 是一种面向连接的协议这一特性。换句话说， LDAP 客户端会打开与 LDAP 服务器的连接，并在同一连接上执行各种协议操作。在连接生命周期内的某个时刻， LDAP 客户端可能会向目录服务器进行身份验证，此时可能会被授予额外的（或更少的）权限。例如，客户端可能以特定身份进行身份验证，该身份已被授予对目录中所有条目的读/写访问权限。在进行身份验证之前，客户端的权限集是有限的（通常是目录所有用户都拥有的默认权限集）。但是，在进行身份验证之后，只要连接保持打开状态，客户端就会被授予扩展的权限。

*身份验证*究竟是什么？从客户端的角度来看，它是向服务器证明客户端是特定实体的过程。换句话说，客户端声明其拥有某种身份，并提供一些凭证来证明这一声明。从服务器的角度来看，身份验证过程包括接受客户端提供的身份和凭证，并检查它们是否能够证明客户端就是其所声称的那个人。

为了用具体的例子来说明这个抽象概念，我们来看看 LDAP 简单身份验证的工作原理。在*简单身份验证*中， LDAP 客户端向 LDAP 服务器提供一个 DN 和一个密码，这些信息以明文形式（未经过任何哈希或加密处理）发送给服务器。服务器会在目录中找到与客户端提供的 DN 对应的条目，并检查客户端提供的密码是否与该条目的 userPassword 属性中存储的值匹配。如果匹配，则客户端通过身份验证；如果不匹配，则身份验证操作失败，并向客户端返回一个错误代码。

对目录进行身份验证的过程称为*绑定* 。当绑定操作成功完成身份验证时，身份就会绑定到连接上。如果客户端未进行身份验证，或者在未提供任何凭据的情况下进行身份验证，则客户端将以匿名方式绑定。换句话说，服务器不知道客户端是谁，因此会授予客户端一组默认权限。通常，这组默认权限非常有限。在某些情况下，默认权限集会完全限制权限：不允许读取或搜索目录的任何部分。如何处理匿名绑定的客户端取决于目录管理员，并取决于适用于您组织的安全策略。

许多不同类型的身份验证系统都独立于 LDAP。LDAPv2 仅支持简单身份验证，其中 DN 和密码以明文形式从客户端传输到服务器。

为了支持多种不同的身份验证方法， LDAPv3 采用了 SASL 框架。SASL 为 LDAPv3 支持多种身份验证协议提供了一种标准方法。每种身份验证系统都对应一个特定的 SASL 机制。SASL 机制是一个标识符，用于描述所支持的身份验证协议类型。

服务器验证客户端身份后，可以根据站点特定的策略授予额外的权限。例如，您可以制定一项策略，允许用户在通过身份验证后搜索目录，但不允许他们修改自己的目录条目。或者，您可以制定一项更宽松的策略，允许某些已通过身份验证的用户修改其条目的某些属性，而其他用户（例如您的管理人员）则可以修改任何条目的任何属性。您对访问权限的描述、授予这些权限的实体以及这些权限适用的目录条目统称为*访问控制* 。

##### LDAPv3 身份验证方法

在 LDAPv3 的开发过程中，我们逐渐意识到必须定义 LDAPv3 服务器必须支持的最低身份验证方法集。如果没有这样的定义，来自不同厂商的客户端和服务器可能除了简单身份验证之外，没有任何共同的身份验证方法。要知道， LDAP 简单身份验证会以明文形式在网络上传输密码，没有任何加密。允许这种情况存在将严重限制 LDAP 的普及。

为了解决这个问题， LDAP 工作组定义了身份验证方法，并在 RFC 2829《 *LDAP 身份验证方法》* 中强制要求实现这些方法。该文档将 LDAP 服务器分为三个不同的组，每个组都有各自的要求：

- 只读公共目录服务器可能允许匿名身份验证（无需密码）。
- 支持基于密码的身份验证的服务器*必须*支持 RFC 2831 中记录的 DIGEST-MD5 SASL 机制， *即使用摘要身份验证作为 SASL 机制* 。
- 需要会话保护（加密）和身份验证的服务器必须实现 RFC 2830 *《轻量级目录访问协议 (v3)：传输层安全扩展》* 中定义的 StartTLS 扩展操作。此扩展操作允许 LDAP 客户端请求对其与服务器之间传输的所有数据进行加密，并允许客户端和服务器使用公钥证书相互验证身份。

当然，任何服务器都可以使用比严格要求更安全的身份验证方法。例如，支持基于密码的身份验证的服务器也可能支持 StartTLS。RFC 2829 的目的是确保任何符合 LDAPv3 标准的客户端都能以安全的方式向任何符合 LDAPv3 标准的服务器进行身份验证，而无需以明文形式发送密码。

##### 访问控制模型

得知 LDAP 目前尚未定义标准访问控制模型，可能会令人有些失望。但这并不意味着各个 LDAP 服务器实现都没有访问控制模型。事实上，任何商业上成功的服务器软件都必须具备这样的模型。

### LDIF

LDAP 数据交换格式 ( LDAP Data Interchange Format , LDIF ) 是一种用于描述目录条目的标准文本格式，定义于 RFC 2849。LDIF 允许您导出目录数据并将其导入到另一个目录服务器，即使两个服务器使用不同的内部数据库格式。在数据库/电子表格领域，制表符分隔格式也发挥着类似的作用：它提供了一种几乎所有电子表格和数据库都能导入和导出的简单格式。

LDIF 文件有两种类型。第一种类型描述一组目录项，例如整个公司目录或其子集。另一种类型的 LDIF 文件是一系列 LDIF 更新语句，用于描述要应用于目录项的更改。以下章节将详细介绍这两种类型。

### 目录模式（Schema）

#### Schema 的用途

Schema 是一组规则，用于确定目录服务中可以存储哪些内容，以及目录服务器和客户端在目录操作（例如搜索）期间应如何处理信息。目录服务器在存储新的或修改过的条目之前，会根据模式规则检查条目的内容。每当目录客户端或服务器比较两个属性值时，它们都会参考模式来确定使用哪种比较算法。

#### LDAP 模式的要素

模式由属性类型、属性语法、匹配规则和对象类组成。

#### 属性

请记住，目录条目包含属性类型和值的集合。 *属性类型* （或简称*属性* ）保存特定的数据元素，例如名称、公司电话号码或打印机的额定打印速度（以页/分钟为单位）。在 LDAP 中，属性类型的定义包括以下内容：

- 用于唯一标识属性类型的名称
- 对象标识符 ( OID )，它还能唯一标识该属性。
- 文字描述
- 关联属性语法
- 一套用于管理比较和搜索的匹配规则
- 使用情况指标（无论是应用程序的使用情况还是目录服务本身的运行情况）
- 指示该属性是多值属性还是单值属性
- 指示该属性是否可以通过常规应用程序进行修改
- 对属性中可存储的值的范围或大小的限制

*属性名称*通常比较简短且略带晦涩，但并非必须如此。属性名称具有以下特性：

- 它们不区分大小写；例如， `cn` 和 `CN` 都指同一个属性。
- 其中使用的字符仅限于 ASCII 字母、数字和连字符；并且必须以字母开头。
- 它们在整个目录服务中必须是唯一的，因为 LDAP 应用程序通常使用名称来引用属性。

在目录服务器数据库中存储的条目中，属性可以关联一个或多个*属性值* 。属性类型的定义包含一个指示，表明该类型是否只允许包含一个值（单值）或多个值（多值）。大多数属性类型都是多值，这也是默认设置。

*属性用途指示符*通常从属性类型的定义中省略，因为它默认为用户应用程序，这意味着该属性是通用的，任何目录应用程序都可以使用。另一种用途类型是操作用途（请注意，X.500 系统支持操作用途的几个子类别）。 *操作属性*由目录服务本身用于管理或系统相关目的，通常由目录服务器自身维护。除非明确请求，否则目录客户端不可见这些属性，并且客户端通常无法修改它们。

#### Object Classes

在 LDAP 中，**对象类（object class）**用于将相关的信息组织在一起。通常，一个对象类用于对现实世界中的某类对象进行建模，例如人员、打印机或网络设备（尽管这并不是必须的）。每个目录条目（directory entry）都属于一个或多个对象类。一个条目所属的对象类名称，总是作为一个特殊的多值属性 `objectclass` 的值列出。

与一个条目关联的对象类集合用于满足以下需求：

- 它决定条目中*必须*包含哪些属性类型。
- 它决定条目中*可以*包含哪些属性类型。
- 它为目录客户端提供了一种便捷的方式，可以在搜索操作期间检索条目的子集。

例如，一个用于存储人员信息的对象类可能要求必须包含姓名，并允许包含特定的可选属性来存储人员的个人和联系信息。如果该对象类名为 `person` ，目录客户端可以通过在其构建的 LDAP 搜索过滤器中添加类似 `objectclass=person` 组件，来提供仅搜索人员条目的功能。

LDAP 对象类的定义包含以下所有信息：

- 唯一标识该类的名称
- 一个 OID ，它还能唯一标识该类。
- 一组强制性属性类型
- 一组允许的属性类型
- 一种（结构性的、辅助性的或抽象的）
